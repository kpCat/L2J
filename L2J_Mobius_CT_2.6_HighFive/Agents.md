## Назначение

Этот файл задаёт обязательные правила работы Codex/AI-агента над проектом Phantom World для L2J Mobius High Five.

Перед любой задачей агент обязан прочитать:

1. `PHANTOM_DEVELOPMENT_MASTER_PLAN.md`
2. `docs/phantoms/CODEX_WORKFLOW_CONTRACT.md`
3. `docs/phantoms/TASK_PACKAGE_STANDARD.md`
4. текущий `docs/phantoms/tasks/NNN-short-name/TASK.md`
5. отчёт предыдущей задачи, если он указан

Конкретная задача определяет scope, генеральный план — направление и архитектурные границы, этот файл — правила исполнения. Если требования конфликтуют, нельзя молча менять архитектуру: нужно остановить опасные изменения, выполнить безопасный аудит и описать конфликт в отчёте.

## Архитектурные правила

### Переиспользовать штатную механику

Фантомы должны максимально использовать существующие механики:

- `Player`
- inventory
- skills
- items
- party
- clan
- trade
- mail
- quests
- PvP/PK/karma
- instances
- raids
- sieges

Запрещено создавать вторую независимую реализацию этих систем без доказанной необходимости.

### Минимальный seam

При зависимости `Player` от `GameClient` искать минимальную безопасную точку расширения:

- headless client adapter
- packet sink
- facade действий
- явный lifecycle
- точечные headless-проверки

Не создавать fork всего `Player`.

### Разделение обязанностей

Не создавать один глобальный менеджер всей системы. Разделять:

- profile/persistence
- materialization
- scheduler
- Utility AI
- plan execution
- navigation
- economy
- memory/reputation
- conversation/Semantic Pack
- population
- metrics

### Никакого потока на фантома

Запрещено:

- отдельный `Thread` на каждого фантома
- постоянный `ScheduledFuture` на каждого фантома без отдельного обоснования
- pathfinding в каждом AI-тике
- синхронная запись БД после каждого действия
- одинаковая частота полного AI для всех фантомов

Использовать общие планировщики, очереди, бюджеты и batch operations.

## Производительность

Производительность — часть Definition of Done.

Обязательные принципы:

- ACTIVE/WARM/BACKGROUND/SLEEPING
- direct-path first
- anchor graph для глобального движения
- локальный A* только при необходимости
- path cache
- cooldown повторного планирования
- общий budget pathfinding
- основной party route рассчитывает лидер
- background-симуляция не разыгрывает каждый шаг и удар
- batch persistence
- лимит материализованных фантомов
- graceful degradation при перегрузке

В hot paths запрещены:

- частые запросы БД
- глобальные блокировки
- неограниченные очереди
- полный обход всех фантомов на каждое событие
- создание больших временных коллекций без необходимости
- повторный разбор неизменяемых XML/config
- строковая конкатенация для отключённых debug-логов

## Логи, trace и метрики

В Java нет стандартного C/C++-подобного препроцессора. Самодельный препроцессор создавать нельзя.

### Обычный режим

Разрешены:

- startup/shutdown
- ошибки
- редкие важные изменения
- агрегированные метрики

Запрещены INFO/WARNING для каждого:

- AI-решения
- шага
- pathfinding node
- semantic token
- изменения HP/EXP/inventory

### Диагностика

Trace включается конфигом и ограничивается:

- конкретными phantom names/IDs
- sample rate
- временным окном
- slow-operation thresholds

Использовать дешёвые счётчики (`LongAdder` или эквивалент), ограниченные histogram buckets и периодическую публикацию.

## Автоматические тесты

Ручная проверка пользователя — только крайняя мера.

Использовать подходящий уровень:

- unit
- DB integration
- headless integration
- deterministic scenario
- performance smoke
- soak

Случайное поведение должно поддерживать фиксированный seed. При падении тест сообщает seed.

Нельзя считать test harness рабочим только потому, что пустой набор тестов зелёный. Нужна отрицательная контрольная проверка.

Не заявлять, что команда прошла, если она не запускалась.

Ожидаемые Ant-цели по мере развития проекта:

- `test`
- `verify`
- `phantom-scenario-test`
- `phantom-performance-smoke`
- `jar`

## Git workflow

Целевая ветка:

`feature/phantom-world`

Перед commit:

1. выполнить проверки из `TASK.md`;
2. выполнить `git diff --check`;
3. изучить полный diff;
4. убедиться, что другие хроники не затронуты;
5. исключить случайные binaries и IDE files;
6. создать отчёт.

Предпочтительный commit subject:

`phantom(task-NNN): short description`

Один основной атомарный commit на задачу предпочтителен. Несколько допустимы только при необходимости и перечисляются в отчёте.

Push обязателен независимо от результата. Force push запрещён.

## Статусы

### SUCCESS

Все требования и проверки выполнены.

### PARTIAL

Безопасная полезная часть выполнена, проект остаётся рабочим, невыполненное перечислено.

### BLOCKED

Задача заблокирована.

При `BLOCKED` агент обязан:

- откатить нестабильный/некомпилируемый production-код
- оставить безопасный аудит, тесты и документацию
- создать честный отчёт
- закоммитить
- запушить

Нельзя оставлять заведомо сломанную ветку только ради commit/push.

## Definition of Done

Задача не завершена только потому, что код компилируется.

Обязательно:

- соблюдены `TASK.md` и master plan
- другие хроники не затронуты
- production-код остаётся рабочим
- config и feature flags документированы
- автоматические тесты добавлены и выполнены
- результаты отражены честно
- нет hot-path log spam
- concurrency и lifecycle обработаны
- ресурсы освобождаются
- транзакции безопасны
- нет очевидного duplication
- отчёт создан
- commit создан
- push выполнен

## Главный принцип

Фантом должен выглядеть живым не из-за потока случайных фраз, а потому что:

- имеет потребности
- принимает мотивированные решения
- помнит события
- несёт последствия
- реально владеет предметами и аденой
- зависит от экономики
- строит отношения
- выполняет или нарушает договорённости
- развивается во времени
- говорит в соответствии с характером, памятью и контекстом

Причинно-следственное поведение важнее количества декоративных функций.
