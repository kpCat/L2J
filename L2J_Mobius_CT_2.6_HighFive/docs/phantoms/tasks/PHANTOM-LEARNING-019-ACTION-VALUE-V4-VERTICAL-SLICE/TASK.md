# PHANTOM-LEARNING-019 — рабочая цепочка «native → обучение → новое решение»

## 1. Цель

Одна большая, но **узкая сквозная** реализация: из подлинного уже сохранённого отдельного DAMAGE/HEAL `TacticalReceiptV3` (при наличии доказанной целостности) получить обучающий пример V4 **без EXP/SP всего боя**; выполнить реальное обновление **компактной** модели; сохранить/холодно восстановить её; подключить явным TEST-only opt-in к существующему выбору законных действий `TacticalPolicyV3`; подтвердить, что обученная модель влияет на ранжирование, а в одном коротком native-сценарии используется только внутри штатного безопасного выбора и выполняется действительное действие. Для FULL нужны все G0–G8.

**Не «идеальная PvP-нейросеть», не массовое обучение всех классов, не ночной тренер**. Это минимальный работающий двигатель, на котором можно строить ночной режим без очередных отказов из-за EXP/SP. Программная stock-тактика — рабочая основа и fallback.

## 2. Обязательный быстрый маршрут исполнения

A. В первые 15 минут определить конкретное read-only извлечение существующих подлинных `TacticalReceiptV3` из 016 (SQL rows/сохранённые native artifacts). Проверить фактические SHA/owner/action/episode; не принимать только агрегат `399`. Если нет достаточного читаемого источника — предъявить точный blocker и остановиться ДО новой реализации.

B. Построить V4 *на базе существующих типов*: компактный линейный контекстный оценщик, read-only импорт, версия и SHA, bounded optimizer. Начать с `DAMAGE`; обеспечить расширяемый `HEAL` интерфейс без заявления о полностью обученном хилере. Не создавать второй планировщик или новую систему боя. Не модифицировать `TerminalRewardReceiptV1` и `ActionAdvantageV2`.

C. Из настоящих исходных событий получить минимум один **действительно принятый** V4 sample, затем провести реальное изменение параметров (не просто загрузку фиксированных весов). Предпочтительно взять >=8 подлинных событий из >=2 эпизодов; если их нет, один native sample может доказать механику, но нельзя заявлять статистическое превосходство.

D. На неизменяемой контрольной ситуации проверить конкретное изменение оценок, а при законном изменении ранга — его отличие от stock, затем холодно восстановить тот же SHA и оценки. Синтетические сценарии допустимы ТОЛЬКО как тест выбора/сохранения, **не** как доказательство реального игрового обучения.

E. Выполнить максимум **одну** короткую изолированную native-проверку с V4 TEST-on: до CUT реальные native owner, Player, skill, target, MP, Geo/LOS; сохранить решение, предоставленные альтернативы, score, fallback reason и фактически выполненный эффект. Использовать Solo, если он быстрее/законнее Party. **Не требовать 3-cell, 51-episode, 72-slot подготовки**. Участие модели в реальном выборе должно быть измерено; считать mere synthetic rank недостаточным FULL. Допускается небольшой новый TEST-only entrypoint к уже существующему Runtime, поскольку именно его запрет заблокировал018, но без нового framework/scheduler.

F. Завершить безопасно: TEST OFF, owned processes 0, порты освобождены, ни один исторический файл/SQL/model/pointer не изменён. Не выполнять FIT старой схемы, EVAL/promote старой модели.

## 3. Что именно считать полезностью

V4 получает immediate **измеренную пользу конкретного действия** от штатного `TacticalReceiptV3.reward` (действительные HP, MP, длительность), с bounded нормализацией; не строит выдуманную оценку неисполненных альтернатив. Игровой EXP/SP, убийство, доля команды, агрессия, дебаффы, контроль и PvP **не являются обязательными** для sample DAMAGE/HEAL. Права и исполнение оцениваются отдельно. Для healer важно полезное фактически восстановленное HP, не «объём каста»; следующее расширение учитывает предотвращённые смерти и роли.

Это **локальная эффективность**, не доказательство ожидаемой победы. Стоимость MP не должна превращаться в запрет спасения себя/группы: критические действия и аварийные heal/owner directives остаются у stock, обучаемый ранжировщик вмешивается лишь в штатный список неэкстренных легальных альтернатив. BSoE/Return/автоматическое бегство как learned policy исключены.

## 4. Что запрещено

- Фиктивные игровые источники для зачёта обучения. Изменение параметров только на фактически наблюдённом результате; офлайн fixtures отдельно помечены NOT_NATIVE.
- Ослабление canonical cast legality, owner/epoch, timing, target, MP, Geo, critical rescue, failed effects. Считать UNKNOWN за 0.
- Изменение production Party/Combat/progression, классовых навыков, экономических правил, rates и серверного AI. Изменение исходного `LearningPolicy` и `TacticalPolicyV3` только точечным opt-in V4, по умолчанию OFF, с быстрым fallback.
- Ретроспективное создание terminal receipts из 016; перезапуск старой кампании, новая 51-эпизодная или 72-эпизодная кампания.
- Изменение старых V3 model/optimizer weights, SQL183, TEST2/DRAFT14/Adam903updates/223epochs/pointer12, native-budget016, старых журналов, Geo203/protected207, MAIN/PLAY, Studio.
- Изменение SQL schema, новая миграция, независимый второй GameServer, новый Git worktree/ветка, force push.
- Автоматическое переключение production на кандидата или утверждение игрового преимущества без независимых сравнений.

## 5. Ключевая риск-развилка

Если за один быстрый источник-аудит не удалось легально импортировать хотя бы один настоящий native receipt, **STOP_019_NATIVE_SOURCE_UNAVAILABLE** с указанием конкретного отсутствующего поля/кода. Не строить «правильный тренер» на fake fixtures ради FULL.

Если V4 offline доказан, но short native cut/selection недоступен в разрешённом бюджете, честный `PARTIAL019_NATIVE_CONNECTION_MISSING`, без дополнительной кампании. Если обученный model не меняет реальных score и веса — `BLOCKED019_NO_LEARNING` независимо от количества пройденных тестов.

Владелец хочет результат, а не фабрику чек-листов: отчёт на 1–2 страницы, плюс машинные счётчики и хеши; не превращать задачу в самостоятельный исследовательский проект.
