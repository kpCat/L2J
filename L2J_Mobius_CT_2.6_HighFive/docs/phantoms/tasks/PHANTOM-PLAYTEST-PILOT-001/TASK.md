## 1. Результат для пользователя

Реализовать локальный серверный пилот для **одного отдельного тестового персонажа с настоящим подключённым клиентом**. После одного входа и явного предоставления доступа Codex запускает несколько проверок подряд из PowerShell: получает состояние, перемещает персонажа, отправляет его сообщения, выполняет обычные party-действия и собирает результаты. Не требовать логина и скриншота после каждой операции.

Это задача реализации и проверки инструмента, не очередной аудит 146 возможностей и не обещание реализовать все возможности ботов за один проход. В этом же изменении разобраться с предполагаемым idle-disconnect и защитой от частых диагностических команд. ## 3. Обязательный функционал

1. Локальный file-mailbox без TCP/HTTP-порта, shell/eval/reflection и универсальных admin-команд.
2. Явная двухсторонняя привязка: локальный оператор готовит одноразовое разрешение, пользователь вводит `.playtest arm <код>` **отдельным** персонажем. По умолчанию предлагаемое имя — `CodexQA`; альтернативу задаёт пользователь. Никогда не выбирать автоматически основного персонажа или первого online игрока.
3. Сессия привязана к каноническому LocalPlay root/owned Game PID + времени старта процесса, account + objectId, конкретному GameClient/session generation, непредсказуемому sessionId, времени окончания. Имя нужно только для первоначального выбора, не для дальнейшей авторизации.
4. `.playtest status`, `.playtest stop`, `.playtest off`: состояние, немедленная остановка сценария, полный отзыв доступа. Нужен и локальный PowerShell stop.
5. Типизированные действия из DESIGN. Все изменения только от имени привязанного Player, через штатные действия/сервисы. Телепорт — явно тестовое позиционирование; он не доказывает работу навигации или материализации фантома.
6. PowerShell-команды Prepare/Get/Invoke/Run/Stop пилота с машинно-читаемыми результатами. Один runner исполняет пакет проверок и пишет один REPORT + RESULTS.tsv. Не нужен новый универсальный тестовый framework.
7. Сохранение живого GameClient и REAL_LOGIN identity. Пилот не создаёт fake/null-network GameClient, не заменяет его headless session, не пишет вручную `online=1`, не логинится за пользователя и не обходит аутентификацию.
8. Раздельный статус `HARNESS_RESULT` и `GAMEPLAY_RESULT`: успешная доставка приглашения не означает, что бот его принял; отправленный пакет не доказывает, что пользователь увидел правильную картинку.

## 4. AFK и flood — диагноз до изменения

Пользователь сообщил предположения, а не подтверждённые причины. Не объявлять найденный по названию timeout причиной его отключения.

- Проследить inactivity/kick/disconnect policy и её вызывающие точки, effective private settings и доступные существующие логи. Проверить отдельно серверную политику простоя, сетевой разрыв/keepalive, остановку сервера, клиентский logout и наказание за flood. Смена скринсейвера или sleep Windows не устраняется серверным флагом.
- Если подтверждена именно серверная политика AFK: точечное исключение только для привязанного пилота во время действующей lease. Остальные игроки/фантомы и реальные сетевые разрывы сохраняют обычный lifecycle. Исключение ставить ДО начала destructive disconnect, не подавлять cleanup после разрыва.
- Если такой механизм не найден/не включён или факт отключения не воспроизводится: сохранить `IDLE_CAUSE_UNCONFIRMED`/`NO_SERVER_IDLE_POLICY_FOUND` и диагностику. Не добавлять бессмысленный глобальный anti-AFK патч и не блокировать разработку пилота ожиданием многочасового кика.
- Проследить реальный `/loc` через `BypassUserCmd` и зарегистрированный IUserCommandHandler; отдельно `.phantomstatus`, `.playtest`, Say2, ChatGeneral и прочие channel handlers. В проверенном BypassUserCmd нет прямого flood/mute; FloodProtectorAction содержит kick/ban/jail, а не универсальное наказание mute. Не подменять это предположением.
- Read-only snapshot пилота должен читать координаты/статус прямо на сервере и НЕ слать `/loc` через chat/пакеты в цикле.
- Разрешить безопасную диагностику без накопления punitive flood-счётчика у **этого** разрешённого персонажа, только на доказанной точке ограничения и по точному whitelist команд. Оставить небольшой локальный rate limit с `THROTTLED`, не mute/ban/kick. При штатном отсутствии такого ограничения никаких новых bypass не нужно.
- Обычный чат, торговля, mail, multisell, item operations, сетевые лимиты и действующий mute другого происхождения НЕ освобождаются от защит. Пилот соблюдает native pacing; не очищает наказания задним числом. `stop/off` доступны даже при chat mute в допустимом voiced path.

## 5. Безопасность и PLAY

Public default выключен. Наличие одного файла `local-play.json` само по себе недостаточно: нужен включённый private pilot config, валидное локальное разрешение и текущая привязка. Не расширять PersonalCharacterQoL allowlist ради пилота: он не должен получить cross-class skills, премиум, предметы или GM.

PLAY: только SELECT/SHOW для диагностики. Обычные серверные действия тестового персонажа и их штатное сохранение разрешены. Запрещены прямые DML/DDL, reset/reseed, ручное исправление/удаление профилей. TEST fixtures создаются только штатным guarded test harness в выделенной TEST DB; не очищать чужой TEST provenance ради зелёного результата.

Не менять population 10000, ActiveTarget=64, MaxMaterialized=128, MaxScheduled=10000, CreationInFlight=2, scheduler pulse/boundaries, rates, геодату, схему и экономику. Не выдавать персонажу уровень, класс, шмот, адену, навыки, бессмертие. Вызов имеющегося навыка не означает выдачу навыка.

Пилот не управляет ботами напрямую: не выставляет им Goals, admission, координаты, HP, party membership, inventory, не вызывает materialize/signal для подделки результата. Отдельный TEST-setup явно отмечается как fixture, не как автономное поведение.

## 7. Единственная плановая пауза пользователя

После всех автоматических gate и готового deployment — один `USER_CLIENT_ACTION`, только если свежая действующая pilot session отсутствует:

«Сервер готов. Создайте/выберите отдельного CodexQA, войдите им и введите `.playtest arm <одноразовый код>`. Оставьте клиент открытым. После этого весь пакет проверок запускаю самостоятельно».

Код приватный, не коммитить и не дублировать в публичных evidence. Пользователь не должен придумывать objectId, искать координаты, выдавать GM или выполнять 10 status-команд. До этой паузы довести всё, что проверяется без его клиента; не возвращать ранний BLOCKED из-за ещё не созданного персонажа.

Нет ответа/клиента — `READY_FOR_CLIENT_BINDING`, это не `GREEN — CONNECTED PILOT PROVEN`. После ответа продолжить эту же небольшую задачу с saved checkpoint. При отключении/рестарте сессия недействительна: не маскировать необходимость нового входа. Не обещать автоматический login.

## 8. Завершение и ограничение затрат

Объединённый connected smoke — ориентир до 10 минут, без 15/45-минутного scale soak. Внутренние subcases выполняются одной командой и одним отчётом; сообщения пользователя между ними не нужны. Не повторять полную сборку/весь пакет после каждой мелкой правки: сначала targeted subtest, затем один итоговый пакет.

На успехе runner прекращает действия, освобождает execution lease и возвращает управление клиенту. Настоящий LocalPlay можно **оставить RUNNING** для пользователя — намеренное отличие от scale-задач. Активного сценария/неограниченной очереди не остаётся. Явная consent lease не продлевается автоматически; указать её expiry и состояние ARMED_IDLE/OFF. При реальной runtime safety-проблеме — остановить только принадлежащие задаче процессы штатно. Никакого обещания, что Codex продолжает работать после финального ответа.

Outputs в текущем task dir: `EVIDENCE.md`, `STATE.md`, `RESULT.md`, `RESULTS.tsv`, `USAGE.ru.md`, `VISION_DELTA.md`. Runtime подробности/permit/queue — private directories, в git не включать. Финал обязан отличать проверку пилота от известных неработающих функций ботов и указать точный scope native/client evidence.

Git: только read-only status/branch/HEAD/upstream/remote/diff/log, exact-path add, commit, обычный push `origin feature/phantom-world`; разрешён чистый detached worktree для build (native isolation или `git worktree add --detach` / remove). Запрещены `git add .`, reset, clean, stash, rebase, force-push. Не коммитить чужое, секреты, JAR, runtime DB/config/mailbox. При более новом HEAD перед write — остановить запись и объяснить, не перезаписывать.
