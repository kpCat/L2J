На каждый следующий шаг оформляется отдельная ограниченная задача после source review.
Если нужен пересмотр подхода, исполнитель приносит boundary, а не расширяет scope.

попытка5 последовательных native farm cycles. Endpoint — кадры и честная матрица.

## V2 — Надёжный локальный native farm

Выбрать решение после V1. Если current path уже дал5 циклов, не писать новый Brain:
закрепить этот путь и проверить контраст fighter/mage дешёвым вторым vertical.
Если не дал — задача лишь по наблюдаемому месту разрыва с точным root cause от архитектора.

Endpoint — самостоятельные5 cycles и применимый loot, не helper-only GREEN.

## V3 — Жизнь между локальными эпизодами

Один сценарий: native death/recovery → несколько успешных farm cycles → REAL уходит →
безопасный soft demat → background continuation → REAL возвращается → remat и farm.
Точечный контролируемый restart проверяет последнюю сохранённую progression/inventory.
Bounded stuck recovery проверяется одним известным локальным препятствием, не всей картой.
Не требовать global walking/GK, все профессии, party/summon roles и экономику.
Сохранность rewards, single owner и b4f protocol не отключаются ради экономии тестов.
Endpoint — одна воспроизводимая end-to-end жизнь на принятой версии, без данных «из воздуха».

## V4 — Приёмка M1

Frozen accepted code, affected targeted regression и независимое ревью именно финального
изменения, clean JAR, controlled deploy. Несколько естественных профилей, два заранее
выбранных локальных места (включая ранее проблемный стартовый участок), доказательства
не одиночного бота. Проверки среды/локаций распределить заранее без повторных blind runs.
Один финальный настоящий клиентский gate со свежим arm и подтверждённым OFF.
Endpoint — materialization/local farm/reward/loot/next target, отсутствие массового
idle/water/stack, bounded recovery, смерть и background/remat поддержаны доказательствами.
После этого M1_CLOSED; до этого M2 не начинается. После runtime RED — точная boundary,
не ещё один полный прогон ради надежды.

## Экономия без ослабления результата

Новые задачи обычного исполнения — High, а не автоматически Very High. Один исполнитель;
review получает замороженное изменение один раз, не несколько постоянно меняющихся trees.
Каждой задаче задать scope, budget и endpoint. Не выводить проценты «M1 готов на95%»
из количества unit tests. Уже доказанный пользовательский vertical не переписывать
только ради теоретически более красивой внутренней схемы.
