## Минимальная запись каждого решения

Одна секция в FIX_REVIEW040.md, без отдельной папки на каждое предположение:
`ID → симптом → root cause (файл/метод/условие) → почему не соседняя причина → RED командой/trace → изменённая ответственность → GREEN → отрицательный случай → native outcome → какие gates инвалидированы/перепроверены`.

На гипотезу достаточно короткого локального теста/узкого trace. Один полезный reproducer лучше десяти новых exporters. Не объявлять root cause по одному совпадению времени или внешне похожему stale state. Когда причина не установлена, использовать UNKNOWN и продолжать целевую диагностику, а не выбирать удобное объяснение.

## Самоанализ после повторного сбоя

После двух неудачных патчей одного класса ответить письменно, не более15 строк:
1. Кто должен был владеть состоянием и кто реально им владел?
2. Событие отсутствовало, было потеряно, применено дважды или пришло устаревшим?
3. Исправлялся источник причины или только симптом/наблюдатель?
4. Какое альтернативное объяснение осталось и какой один тест различит варианты?
5. Какой минимальный связанный рефакторинг делает переход явным и проверяемым?

После этого разрешён один пересмотренный цикл с причинным тестом. Повторения без новой информации не продлевают кампанию. Независимые исправимые дефекты продолжать закрывать; недоказанный остаток не скрывать.
