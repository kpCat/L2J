## Что действительно предлагает исходный текст

Разделы оригинала: существующие решения; навигация; логика целей/поведения; server/headless/hybrid; архитектуры A1/A2/A3; рекомендации/миграционный план. Предпочтение отдано серверному AI с постепенной доработкой Autoplay и возможным применением gdx-ai/Recast4j. Упомянуты target selection, устранение залипания, death/recovery, роли группы.

Но в приложенном тексте нет точных ссылок на методы/строки текущего Phantom-кода, сопоставления с03x ownership/epoch/earned protocol, измерений BASE040 или проверенного migration patch. Поэтому текст не закрывает ни один gate M1 и не разрешает немедленно заменить работающие механизмы.

## Ограниченная проверка по первичным внешним источникам

1. README L2jRoboto описывает fake-player engine для aCis372 с расширением FakePlayerAI, а не готовый самостоятельный сетевой headless-клиент. Поэтому предложение оригинала использовать «L2jRoboto в режиме headless» как готовую клиентскую основу не принимается без отдельного подтверждения. В040 это не путь реализации.
2. README gdx-ai подтверждает Java-инструменты state machines/behavior trees/pathfinding, включая hierarchical/interruptible pathfinding, и зависимость от libGDX JAR. Это общая библиотека алгоритмов, а не готовые правила High Five, capability/epoch ownership или слой сохранения. Непригодность для многоэтажного графа сам исходный отчёт не доказывает.
3. Recast4j действительно является Java-портом Recast/Detour navmesh toolset. Но этим не доказана совместимость конкретной геодаты Mobius, её door/instance/layer semantics, памяти и authoritative native movement. Перед такой интеграцией нужен отдельный проверенный geometry-adapter; в040 его не разрабатывать.

Первичные источники, проверенные при подготовке 12.10.2026:

```text
https://github.com/Elfocrash/L2jRoboto
https://github.com/libgdx/gdx-ai
https://github.com/recast4j/recast4j
```

Остальные утверждения внешних проектов из оригинала не проверены здесь по исходникам и не считаются production-фактами.

## Инженерное решение для040

Принять намерение: server-native архитектура, capability-based поведение, общий поиск допустимого action position, явно завершённый feedback loop, штатное восстановление, работающие lifecycle/background переходы.

Не принимать как техническое задание040: отдельный поток на каждого бота; новый Phantom manager вместо существующего; слепой teleport при stuck; альтернативный protocol/headless client; подключение gdx-ai/Recast4j ради наличия библиотеки; переписывание geodata или мозг на C#/LLM. Это выбор области задачи, а не утверждение, что перечисленные технологии вообще бесполезны.

Использовать отчёт для вопросов code review: «почему цель пригодна?», «как найден путь?», «кто замечает неудачу?», «как recovery возвращает к полезной работе?». Отвечать реальным current-кодом/тестом. Если будущая архитектурная альтернатива интересна, оставить одну короткую строку в итоговых рисках, не начинать M2–M7/новую исследовательскую кампанию.
