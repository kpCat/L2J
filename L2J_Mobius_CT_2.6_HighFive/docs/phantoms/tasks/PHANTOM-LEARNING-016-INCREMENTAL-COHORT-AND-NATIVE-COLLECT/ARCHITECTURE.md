# Архитектура 016: порционная подготовка, целостные пары и один тренер

## Главный принцип

Не нужен перебор всех комбинаций до одного запуска. Надо сохранить **один завершённый кандидат** (две свежие A/B pre-CUT руки) и перейти к следующему, пока не покрыты предзаданные требования. Даже если следующий кандидат отказал, предыдущий останется записанным. Прерванная работа не превращается в green.

Поток: `source/inventory snapshot → candidate → native pre-CUT STOCK → native pre-CUT LEARNED → MATCHED_PRECUT commit → next candidate → coverage(3cells, 2classes, Solo+Party) → atomic sealed cohort → recheck live world → TRAIN native CUT/effects → optional FIT`.

**Один и тот же owner** для существующего GameServer и native cast. Новое программное руководство процессами (supervisor, planner engine, scheduler) не создавать. Уже существующий `Training.ps1`, `PhantomAutonomousTrainingNative`, `AutonomousTrainingV1`, `TrainingStore` и `TacticalStoreV3` должны использоваться по их каноническим контрактам.

## Что допускается оптимизировать

1. Перенести запись подтверждённой A/B пары ближе к моменту, когда обе стороны уже прошли native admission, **в пределах частного TEST-кохорта**, не меняя production ABI.
2. Создать append-only индекс/курсор именно для выбранного 016-контракта; по нему возобновлять последовательный отбор. Детерминированный порядок не меняется после сохранения кандидата. Повтор не должен выбирать более удобную сцену после просмотра результатов.
3. Не трогать старые Java adapters/ввод сквозных новых workflow: нет second owner, отдельного SQL schema, изменения награды или модели.
4. Стартовать именно с `episodesPerBatch=51`/3 уникальных cells и остановить отбор при достижении полного требуемого покрытия, вместо слепого выполнения остатка 48 planning attempts. Если первые три не покрывают Solo+Party/2classes — продолжить искать, но в пределах фиксированных лимитов/учтённых отказов, без подмены условий.
5. Live-выполнение всегда заново воспроизводит персонажа/цель и повторяет все проверки. Старые `objectId`, `epoch` и live NPC не используются как повторно действительные объекты после остановки.

## Нельзя смешивать три сущности

- **План сцены:** описание источника, набора навыков, целей, исходных фактов.
- **Подтверждённая pre-CUT A/B пара:** две свежие проверенные симметричные пробные подготовки, никакого урона/награды/credit.
- **Реальный учебный эпизод:** фактический native CUT, выбранное действие, платный эффект/терминал, учёт в соответствии с разбиением TRAIN/TUNING/AUDIT.

Упрощения `PAIRED_PRECUT == PAID_TRAIN`, `valid yesterday == native legal now`, `timeout == sample insufficiency` и `death == invalid` категорически запрещены.

## Восстановление

При STOP, PAUSE, TIMEOUT или аварии требуется безопасный cold read: валидировать immutable files/byte hashes и lineage, проверить незавершённые reservations, затем продолжить **только то**, что не завершено и может быть законно повторно воспроизведено. Возврат к живому NPC, если его уже не существует, запрещён. Если source/ability/world изменились — `STALE_RECHECK_REQUIRED` либо блокировка и новый scoped кандидат, без тихой подмены.
