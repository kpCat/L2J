# PHANTOM-FARM-ECONOMY-066 — полезная жизнь, добыча и разгрузка

Дата решения владельца: 21.10.2026. Это feature campaign, не повторное закрытие M1–M7.
Цель: персонаж самостоятельно сражается без сосок, собирает законный дроп, спойлит, распоряжается излишками и возвращается к жизни; новые местные персонажи не ждут окончания ленивой дематериализации только из-за мягкого лимита.
Стек: существующие Java High Five/JDK25/Ant/MariaDB. Новых библиотек и второго AI/economy engine не нужно.
Исполнение: один новый диалог Codex, последовательные законченные этапы. AUTHORITY.md содержит заранее выданные разрешения; этапы не требуют подтверждения владельца.

## 2. Предварительный аудит — один компактный проход
По READ_SET.md определить фактические точки исполнения, writers/leases/locks, поля состояния и имеющиеся проверки. Записать краткий PLAN066.md в этой папке, затем немедленно выполнять; approval gate отсутствует.
Аудит должен различать выбор действия, native исполнение и подтверждённый результат. В частности, существующий SELL handler не равен автономной продаже, а успешный doCast/pickup request не равен награде.
Начальные артефакты пакета неизменяемы. Результаты добавлять отдельными файлами; не редактировать PACKAGE_SHA256.txt под новые результаты.

## 3. Исполнение: обязательный порядок и законченные этапы
Каждый этап: причинный RED → минимальное общее исправление → affected GREEN → интеграция в обычный runtime. Реальный fixture failure не выдавать за product RED.
При одном заблокированном участке продолжать независимые разрешённые участки, не запускать несвязанные новые направления.

### A. Бой и полезное снабжение
- [ ] Разделить отсутствие усилителя и запрет native действия. Отсутствие Soulshot/Spiritshot/Blessed Spiritshot, неверный грейд сосок или исчерпание запаса не запрещают законную атаку/заклинание.
- [ ] Сохранить платную native зарядку из имеющегося stock; не создавать заряды, Adena или предметы. Проверить SS, SPS, BSS, истощение посреди боя, оружие без расхода shots и затронутый summon path.
- [ ] Не превращать stale owner, закрытый admission, persistence incident или ошибку списания в разрешение атаковать. Lifecycle fences и native MP/HP/reagents/arrows/reuse/target/geometry проверки остаются.
- [ ] Исправить выбор снабжения: без бюджета не повторять невозможную покупку/путь каждый тик и не вытеснять доступный бой. После изменения средств/stock снова разрешить экономически разумную закупку.
- [ ] Обновить связанные background оценки только там, где тот же обязательный shot-контракт блокирует обычный фарм; одинаковая семантика, без двойной награды World/Background. Реальные обязательные боеприпасы не отменять.

### B. Подбор и Spoil/Sweeper в той же игровой петле
- [ ] Переиспользовать AutoPlay/AutoUse/PhantomVisibleAutoPlay/CombatBackend. Один согласованный хозяин текущего действия; не запускать конкурирующий pickup-loop.
- [ ] Подбирать доступные вещи любого законного происхождения, а не только дроп текущего NPC/убитого лично моба. Окончательное право решает текущая native защита/party/quest policy, НЕ killer==picker.
- [ ] Устранить голодание pickup/sweep из-за немедленного нового target, HOLD/directive, yield на supply/learning и слишком узкой зоны после дальнего боя. Расширение только ограниченное и настраиваемое, не scan всего World.
- [ ] Сначала угроза/выживание; затем законный скоропортящийся sweep и доступная ценная добыча; несколько ближайших вещей за ограниченную серию; затем фарм/логистика. Не бросать обязательную поддержку Party ради Adena.
- [ ] Выбор: полезность/ценность, стоимость пути, риск, вместимость/вес. Короткая память отказов с повторной проверкой после истечения защиты/смены условий; vanished/занятый/недостижимый объект не зацикливает actor.
- [ ] Проверять живую цель для Spoil и законный труп для Sweeper раздельно. Использовать реально известные skills, штатный шанс и spoil tables; не setSpoiled/ручная выдача материалов.
- [ ] Разделить combat progress и хозяйственный progress: настоящий pickup/sweep полезен, но не должен скрывать сломанный бой. Party-distribution и merge стаков подтверждать по native результатам, не по одному общему изменению inventory count.

### C. Мягкая materialization capacity + ленивая дематериализация
- [ ] Расширить существующие MaterializationService/Retention/Reconcile/Scheduler/Locality/Ecology, не создавать вторую систему. Рабочий cap — целевое количество, не условие обязательного ожидания свободного старого места.
- [ ] Добавить один параметр резерва превышения (предлагаемое имя `PhantomMaterializationBurstSlots`, либо существующий эквивалент). Совместимость: 0 сохраняет strict policy; предел физических admission = soft target + burst. Счётчик включает загружаемые и retained/failed owners до настоящего освобождения.
- [ ] В candidate066 включить резерв; стартовый безопасный профиль soft16 + burst16, либо обоснованная не меньшая проверенная конфигурация. Это не обещание сотен видимых actors; population/active/readiness budgets должны реально пропускать этот резерв.
- [ ] Новый актуальный local demand при наличии резерва материализуется ДО cleanup старого невидимого actor. Пока запас есть, не обходить hysteresis немедленным eviction только ради soft target.
- [ ] Старые невидимые actors сохраняются на действующий grace, затем уходят штатно, даже без нового cap-pressure. После grace прекратить новые обычные roots, дождаться earned work и сохранить ровно один раз. Возврат наблюдения до seal отменяет устаревшее намерение retirement.
- [ ] Visible/Party/Store/in-flight/earned/persistence/hard holds не вытесняются ради лимита; ошибка cleanup не освобождает фиктивное место. При hard ceiling — честная очередь с причиной, не бесконечный рост и не force delete.
- [ ] Метрики: target, physical ceiling, occupied/reserved/retained, excess, возраст ожидания/cleanup и blockers. Проверить все потребители availablePermits/maximumMaterialized, не только конструктор Semaphore.

### D. Распоряжение добычей: NPC, склад, кристаллизация
- [ ] Общая ограниченная политика `KEEP/SELL_NPC/WAREHOUSE/CRYSTALLIZE/MARKET_RESERVE`, основанная на item/recipe/skill data. Новая политика использует имеющиеся owners; это не отдельная валюта/инвентарь/рынок.
- [ ] В первую очередь защитить надетое, нужные расходники/боеприпасы, ближайшую замену экипировки, активные recipe/quest/skill needs, reservations/trade и явно редкие вещи. Неизвестная классификация → сохранить, а не уничтожить.
- [ ] Базовое решение владельца: ненужные No-grade и низкоценные D/C key-parts → NPC; B/A/S+ key-parts и enchant scrolls D+ → хранение/рынок. Не считать все MATERIAL дешёвым хламом: recipe ingredients могут обслуживать несколько грейдов, брать старшую/защищённую роль и разумный reserve.
- [ ] Грейд key-part определять по существующим рецептам и продукту, а не по NONE-грейду ингредиента или тексту имени. Общие ресурсы, рецепты, crystals, soul crystals, Life Stones не попадут в массовую дешёвую продажу.
- [ ] Завести ограниченный инвентарный maintenance intent на существующем journey/candidate механизме: нехватка места/денег или возвращение в город → продать ненужное → сложить ценное → купить нужное → вернуться к исходной цели. Пороги low/high watermark, cooldown и ограниченная пачка исключают поход после каждой вещи.
- [ ] SELL проводить через существующий PhantomCommerceService/L2jCommerceBackend и native цену. Выбирать доступный Merchant с валидным buylist, а не NPC по зашитому имени/координатам. Не отключать AllowRefund/zero-sell policy ради PASS: адаптировать затронутый путь к stock правилам или явно отметить unsupported и безопасно отложить продажу.
- [ ] Склад — настоящий PlayerWarehouse с native slots/stack merge, платой и ограничениями. Deposit/withdraw через существующие container primitives с корректным owner/receipt; при необходимости минимальный shared seam, не исполнение client packet через fake GameClient.
- [ ] При полном складе/нехватке платы: ограниченный запас в inventory, продажа только разрешённых излишков и повторная оценка pickup. Не расширять лимиты, не уничтожать редкое, не крутиться в вечном bank loop.
- [ ] Вывод из банка: перед закупкой учитывать уже имеющийся запас; изъять нужное для снабжения/экипировки/известного торгового плана с проверкой inventory capacity. Для существующей SELL-лавки вещь сначала реально возвращается в inventory, не продаётся одновременно из двух мест.
- [ ] Кристаллизация — `CrystallizationService.inspect/crystallize`, настоящий уровень навыка и фактический yield. D/C излишки разрешены при выгоде/собственной потребности; B+ по умолчанию сохранять, opt-in только с надёжной оценкой. Эпики/редкое/надетое/улучшенное/зарезервированное автоматически не ломать.
- [ ] NPC sale создаёт Adena один раз; warehouse fee и покупка списывают её один раз; crystal conversion уничтожает исходную вещь. В full/inconsistent/ошибочных состояниях не выдавать компенсацию вслепую.
