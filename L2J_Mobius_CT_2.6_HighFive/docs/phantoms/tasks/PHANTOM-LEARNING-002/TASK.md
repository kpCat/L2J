# PHANTOM-LEARNING-002 — автономный тренажёр Phantom World (Training Director)

## 1. Идентификатор
PHANTOM-LEARNING-002. Отдельная новая задача Codex. Reasoning: Very High. Исходный commit GitHub: `b85dd2a3a5f6f153c77b02f1e4887c490eb08ea8`, ветка `wip/phantom-learning`. Новый scoped WIP: `wip/phantom-learning-002` в **независимом** клоне/worktree. Модуль `L2J_Mobius_CT_2.6_HighFive`.

## 2. Цель
Создать реально автономный TRAIN-контур: владелец запускает `TRAIN_START.cmd` и закрывает Codex; независимый процесс Training Director сам подготавливает легальные тренировочные эпизоды на отдельном L2J GameServer, собирает NATIVE игровой опыт, сохраняет историю, выполняет периодическое offline обучение/проверку, обслуживает `STATUS/PAUSE/STOP/REPORT/EXPORT` и переживает закрытие вызывающего терминала и штатный restart. Для пользователя — статус и итог по-русски без необходимости чтения Java stack traces. Нельзя сделать один очередной жёстко закодированный сценарий с шестью Archmage и назвать это директором.

## 3. Зависимости / исходный результат
LEARNING-001 доказала v2 ACCEPTED MLP, изменение Prominence 1230:28 → Fire Vortex 1339:1, законный фактический урон в Solo 1563 HP и Party 1203/1408 HP, 47 уникальных NATIVE events, независимый audit 0.057480 против среднего 0.072036 и cold SQL reload. Точные данные и безопасные команды в `docs/phantoms/tasks/PHANTOM-LEARNING-001/HANDOFF.md` и `docs/phantoms/reports/PHANTOM-LEARNING-001.md`. Это НЕ доказательство общего PvP/Heal/спойла или прироста DPS.

## 4. Контекст / конечная цель проекта
5000 persistent identities, >=128 materialized (250 offline stores НЕ входят в cap), умный PvE/PvP/PK, Party, классы/сабклассы/экипировка/бафы/соски, геометрия, саммоны, позднее рейды/осады/TW/Олимпиада. Training Director V1 НЕ должен реализовывать весь этот AI за один goal, но должен быть ОБЩИМ инфраструктурным инструментом с расширяемым форматом режимов и действующих возможностей. Полная Party/Combat/game-state корректность не может подменяться данными из упрощённой модели.

## 6. Архитектурное решение
**Один Training Director, один контракт Scenario→Episode→Evidence→Dataset→Candidate→Evaluation→Checkpoint.** Директор — самостоятельный bounded процесс, отдельный от сеанса Codex. L2J GameServer остаётся source of truth. Native runtime с настоящими `Player`, навыками, World/Party/Combat, Geo и нормальной экономикой; генератор выбирает законные стартовые условия. Offline тренер обучает текущую модель, сохраняет версии. Использовать имеющиеся механики; не создавать дубликаты GameServer, Combat, PathFinder или Reward engine.

Состояние директора долговременно: run id, scenario id/seed, phase, attempt, checkpoint, suite fingerprint, model version, owner PID/creation time, GC/CPU budgets, last heartbeat. `STOP`/`PAUSE` должны быть штатными и возобновляемыми. Нет постоянного потока на персонажа. Нет SQL на каждом ударе.

## 7. Scope — что РЕАЛЬНО сделать
1. **Первый запуск одной командой** на Windows 10/11: `TRAIN_START.cmd`, `TRAIN_STATUS.cmd`, `TRAIN_PAUSE.cmd`, `TRAIN_RESUME.cmd`, `TRAIN_STOP.cmd`, `TRAIN_REPORT.cmd`, `TRAIN_EXPORT.cmd` (можно .ps1 с cmd wrappers). Автономность означает: после закрытия исходного PowerShell и Codex процесс продолжает делать новые эпизоды, НЕ только ждать. Для каждого действия нужны ясные русские сообщения, статусы, коды выхода. START идемпотентен; STOP не убивает чужие PID.
2. **Подготовка тестового полигона** самостоятельно из read-only доверенных локальных assets: отдельный каталог, полный штатный SQL installer + learning schema, отдельная MariaDB на loopback, 203 Geo files с SHA, отдельные GameServer/SQL порты, UID/SID/PID/FILETIME/хеши и фактический loopback listener; уникальные run/attempt ids. Существующие рабочие TEST130 / cycle19 / MAIN/PLAY/TEST129 только читать, не мутировать. Привязка GameServer уже исправлена; не обходить её.
3. **Генератор сценариев с сохранённым каталогом**: не хардкодить один NPC или класс. Выбор из действующих данных класса/уровня/изученных навыков/экипировки/бафов/типа монстра/скопления/позиции/Party 2..9/среды; сначала поддержать реальные legal Solo и Party PvE V1 c 2+ атакующими способностями. Категории `PVP`, `PK`, `RAID`, `SIEGE`, `TW`, `OLYMPIAD`, `SUMMON`, `HEAL`, `CONTROL`, `SPOIL/SWEEP`, `MOVE` зарезервировать в versioned схеме и отчётах как `NOT_IMPLEMENTED` — не генерировать фиктивный Native для них.
4. **Адаптивный выбор эпизодов**: детерминированная очередь из seed + конфигурации + coverage ledger. Если одно игровое поле/состав не прошло safety/Geo/точный source/stock Party readiness, записать код причины и попробовать следующую законную комбинацию. Не ждать бесконечно одну точку и не останавливать кампанию из-за одного неподходящего spawn. Не ослаблять owner/Geo/SP/EXP/GK/safety/credit.
5. **Один или несколько эпизодов за один GameServer bootstrap**, со штатным Combat terminal consume, canonical Party release, STORE, clear World, естественным респавном/отходом, неповторяющимися action event ids, без ручного редактирования состояния посреди CUT. Подготовить следующий эпизод только на законной границе сценария в собственном disposable TEST. При невосстановимых/опасных состояниях — законная смена актёра/сценария. После завершения лимита батча — штатный STOP и чтение SQL.
6. **Обучение без Codex**: когда достаточно реальных достоверных событий по двум scope и независимым актёрам, директор сам вызывает существующий offline trainer, оценивает кандидата и проводит cold-ON тест в собственном TEST при безопасной границе между сеансами. Модели `ACCEPTED` только после независимой проверки; возможен отказ/пауза при недостатке данных. Никакого автоматического импорта в рабочую игру. Статусы включают причины непринятия и качество по Solo/Party отдельно.
7. **Сохранение опыта для следующих версий ИИ**: помимо v1 numeric features сохранять compact versioned episode record с наблюдаемыми исходными фактами, списком допустимых предложений и решений, фактическими native событиями/исходом и ссылкой на действительные участники/состав/мобов без приватных секретов. Обязательные masks для отсутствующих/не наблюдаемых данных, каноническая provenance `NATIVE` vs `SIMULATED` vs `UNKNOWN`; новые режимы смогут дополнять, а старые записи нельзя переименовывать в native. Retention/stream/export без unbounded RAM/DB. Подумать о дальнейшем обучении по навыкам, Heal и кайтам, но не писать их механику сейчас.
8. **Автономная эксплуатация**: при падении owned процесса или Windows restart — корректное распознавание предыдущей сессии, fail-closed при чужих PID, отчет, допустимое возобновление без двоения наград/actors/events, без стертых логов. Ограничение CPU/параллелизма/памяти/диска и throttling; UI/CLI русские. Возможность менять сценарии и seed без Java rebuild, с versioned config. Первый запуск не требует дополнительной ручной настройки пользователя.
9. **Опциональная точка подключения наблюдателя** — read-only журнал на русском: кто атаковал, кого лечили, что выбрал ИИ, почему сцена отложена, сколько заработано. Полный GUI/вход в клиент НЕ обязателен в 002, но не блокировать будущий spectator.

## 8. Out of scope
Новая 4–8 MB модель, CUDA/PyTorch тренер, перенос всех режимов на обучение, большие боевые стратегии, саммоны/лимиты/Olympiad, полное исправление TASK130, автоматический продакшен-deploy, 5000 активных JVM Player и native 128 simultaneous. Это позднее LEARN-003/004 и TASK131–136. Не менять PVP/PK native rules, дроп/EXP/SP, формулы урона, NPC, skills, цены или права персонажей ради красивых метрик.

## 9. Конфиги
Новые параметры через owner `TRAIN_CONFIG.ini`/другой явно документированный versioned формат: `mode=SOLO/PARTY`, `seed`, `classes/level bands`, `minScenarios`, `maxActiveActors`, `CPU budget`, `memory budget`, `episodesPerBatch`, `trainingThreshold`, `diskRetention`, `evaluationEvery`, `checkpointEvery`, `testLoopbackEndpoints`. Значения и safety defaults из preflight. Не обязательно именно эти имена, но каждое изменяемое правило — извне; никакого hardcoded immutable 3-actor 2-NPC сценария.

## 10. Производительность
Раздельно измерить: время engine startup, подготовка эпизода, native encounter, throughput эпизодов/час, NATIVE evidence/час, full native decision p50/p95/p99 (включая построение признаков), CPU/RAM/диск, DB write, train duration, checkpoint readback. Ограничивать число concurrent materialized actors и работу по биологии ноутбука; отсутствие 128 native proof не выдавать за выполненную цель масштаба. Будущая RTX A5000: расширение training executor допускается без переделки GameServer, но CUDA не обязательна для маленькой текущей MLP.

## 11. Конкурентность, lifecycle
У каждого процесса/сцены/эпизода точный generation/owner/token; никакого отменения чужих действий. Закрывать native leases и Adventure actions до dematerialization; не завершать Combat с активным эффектом, не выдавать повторных HP/loot receipts. Command operations `start,pause,resume,stop,status` идемпотентны, проверяют owned run; stale callbacks и рестарт не могут восстановить чужую сессию. После штатной остановки нет собственных SQL/GameServer/listener/worker остаточных процессов.

## 12. БД и транзакции
Только own disposable schema. Таблицы и migration versioning под директор и episode (отдельные от production profile DB). Immutable event keys, exact native causal identity и CAS для принятых checkpoints. Dirty/partial-эпизод маркировать INCOMPLETE и не обучаться на неподтверждённых данных. SQL batch writer. Проверить холодное восстановление и idempotency, отсутствие cross-schema writes, script data-source guard. Модель `ACCEPTED` применима только при совпадении schema/catalog SHA.

## 13. Автоматические тесты
Тесты генератора/семантики классов, seed reproducibility, coverage, scenario bounds, safe skip & retry, stale epoch, duplicate native receipts, event provenance, crash/resume/checkpoint, PID/port/G0, failing model promotion, unsupported mode, config reload at safe boundary, no mutation user environment. Требовать RED→GREEN для найденных существенных дефектов. После unit и SQL proofs — native test. Не подменять real gameplay mock-only тестами.

## 15. Приёмка — см. ACCEPTANCE.md
На одной fully owned installation: пользовательским `TRAIN_START.cmd` без Codex запускается director; после выхода parent терминала делает следующие NATIVE episodes и подтверждённые exact events в двух PvE scope; TEST самостоятельно запускает обучение/сравнение и сохраняет как минимум кандидат DRAFT; после корректного независимого качества может принять его и холодно загрузить; `TRAIN_STATUS/REPORT/STOP` работают; checkpoint сохраняется и resume по own state; bounded campaign выбирает другие допустимые сцены вместо зависания в WAIT; все защищённые среды остались byte-identical. Не расширять задачу при блокировке чужими игровыми режимами.

## 18. Поведение при блокировке
Не блокироваться из-за отсутствующего готового runtime: создать собственный. Нет количественного лимита bootstraps; каждый запуск должен иметь гипотезу и expected proof. Не запускать бесконечный цикл диагностик при отсутствующем движении в production; сохранять содержательный HANDOFF.
