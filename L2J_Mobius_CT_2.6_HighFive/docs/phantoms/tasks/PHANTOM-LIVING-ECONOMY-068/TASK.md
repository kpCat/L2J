## B. Упрощённая, но согласованная фоновая экономика

**Разрешённое ускорение:** ненаблюдаемую работу агрегировать в существующей Background-модели по времени, доступным источникам, capabilities и расходам. Не проигрывать тысячи ударов и все шаги невидимого пути. Bounded travel допускается между проверенными legal anchors с учтённым временем/платой, если нет реального наблюдения, партии с человеком, store/pending action или другого защищённого владельца. При появлении человека корректно закончить/прервать операцию и материализовать законное состояние; на глазах не телепортировать и не печатать награды.

Использовать existing BackgroundTransaction/Acquisition/Economy receipts. Для каждого начисления нужны source kind, identity, интервал/nonce, входы, расходы и результат; повторный replay/restart не начисляет второй раз. Не создавать вторую универсальную БД, WAL или параллельный inventory. Денежные источники (drop/NPC liquidation), переводы между персонажами и sinks учитываются раздельно. Нельзя за одну операцию заплатить native награду и вторую Background награду. Применять native rates ровно один раз, caps/offline elapsed budget и сохранённый cursor.

**Старт торгового мира:** не ждать реальных месяцев фарма. Разрешены ограниченный исторический warm-start через B либо явно настроенный одноразовый `BOOTSTRAP_CAPITAL/STOCK` для **новых** merchant identities. В обоих случаях — общий серверный лимит и лимиты на item/identity, сохранённый факт выдачи, происхождение и отчёт. Bootstrap — не «заработано в live». Не сбрасывать лимит при restart, пересоздании роли, закрытии лавки или смене конфигов. Нет безлимитных запасов; S/S80/эпики не добавлять в бесплатный обычный seed. После начального заполнения только покупки, крафт, добыча/учтённая фоновая работа и реальные переводы. Merchant bootstrap не должен попутно запускать стартовый фонд5000 боевого новичка и превращать создание торговцев в источник бесплатных сосок; права уже существующих farmer identities не менять. Общий выданный бюджет не сбрасывается удалением/заменой merchant identity.

Эпики: отдельный rarity/effect-aware класс цены; Ring of Queen Ant не считать дешёвым обычным B. Не продавать NPC/кристаллизовать, полезное можно носить. Рынок получает только реально принадлежащие предметы, с редким/нулевым предложением, без гарантии постоянного наличия. Использование NPC/ordinary loot estimator для эпика без валидного источника закрыто. Виртуальные победы над живыми мировыми эпиками **не считаются уже реализованными**; новый raid simulator в068 не строить. Независимый конечный epic seed допускается только как явный выключенный по умолчанию операторский профиль, с отдельным per-item/global quota и точным обозначением искусственного источника; в стандартном кандидате его не включать.

## C. Действительно массовый offline-рынок

Продуктовая цель кандидата: **200 одновременно существующих, не пустых native offline-лавок** по нескольким валидным городским участкам; конфиг позволяет менять число/состав/локации, не hardcode200 в логике. Состав — SELL, BUY и после D MANUFACTURE; не200 копий одной вещи. Отбор ассортиментных категорий общий для ordinary и merchant roles: оружие/броня/Common, расходники, crystals, enchants, recipes/materials; данные D/C/B/A/S/S80 учитываются без выдуманных item IDs. Не заставлять каждую лавку продавать все грейды.

Выбранная архитектура: настоящие Mobius Player/TradeList/PrivateStoreService/OfflineTraderTable, но **выделенная устойчивая merchant-роль**, не сотни боевых ACTIVE AI. Допустим узкий новый owner/adaptor для offline-роли в существующих components, но не второй рынок и не fake GameClient. Отделить торговый бюджет materialization от active battle soft/burst ceiling; старые ограничения TASK065/066 и protected party/store semantics сохраняются.

Критическое: один Player/objectId/identity имеет один lifecycle-владелец. При передаче active→offline остановить его combat/movement/decision/background writers, завершить pending mutations, закрепить store owner; после restart stock restore и Phantom restore **не создают два Player**. Порядок bootstrap/store restore и eligibility старых profiles документировать. Закрытие/исчерпание лавки/переход обратно не теряют вещи. Не убирать store на глазах ради soft cap. Ordinary пользовательские offline-лавки не затрагивать. Не чистить глобально offline tables ради phantom-recovery; обработать legacy stock `storeOffliners`/shutdown совместимо, без второго конкурентного bulk save.

Отсутствуют отдельный timer/thread/полная AI-итерация на каждую лавку. Native регенерация, необходимая платному craft, не должна случайно отключаться вместе с боевым AI; её существующий механизм сохраняется и учитывается в замерах. Shared bounded rotation с индексом due owners, редкое обновление ассортимента и остатков; нативные transaction callbacks запускаются по сделке. Использование памяти Player остаётся реальным — не обещать «нулевую RAM». Контролировать общий hard cap, batch admission, отсутствие занятого цикла/частых одинаковых SQL. Нельзя спрятать200 боевых тиков лишь увеличением интервала.

Позиции: проверенные Geo/Z/town/instance, расстояние между лавками, не NPC/gatekeeper/двери/точки телепорта. Сначала небольшая группа, потом короткий200-merchant sample. Не идти ногами всеми200 через город: новые невидимые merchant identities можно материализовать в заранее допустимых местах согласно общей политике присутствия.

Native BUY резервирует реальную Adena; SELL — существующие экземпляры/count. Update listing не клонирует inventory; между ordinary owner, warehouse, customer и store нет двойного владения. Штатный клиент должен видеть реальные торговые окна и совершать сделки. Без клиента это доказывается native transaction и packet payload, визуальное отображение честно отложено.

## D. Производство, manufacture и экипировка

Переиспользовать RecipeData/RecipeList, native private craft/self-craft, навыки и реальные ресурсы. Гномы продают **услугу** manufacture с известными рецептами и конфигурируемой платой; клиент предоставляет ингредиенты, native механизм определяет расход, MP/время/шанс/результат и оплату. Не списывать материалы дважды и не выдавать готовую вещь скриптом вместо craft. Автоматический self-craft использует тот же план реальных компонентов; общий материал не помечать «D-хламом» по одному рецепту.

Существующий `manufactureFee=0` заменить безопасной политикой платы за услугу из конфигов/recipe difficulty/time/grade. Это авторский экономический параметр, не поддельный stock факт. Не ждать несуществующей «канонической ненулевой цены».

Экипировка: общий evaluator по native class/level/grade penalty, доступным skills, weapon/armor role, set bonuses и бюджету. Реализовать не каталог одной тренировочной профессии, а доступность No-grade→D/C/B/A/S/S80 для разных archetypes. Проверка данных широкая, реальные примеры — fighter/mage/spoiler/support и по одному действительно сменённому mid/high-grade комплекту. Предмет получается через paid NPC/private buy, warehouse, craft или B-source; не бесконечное бесплатное S80.

Покупка/переодевание не прерывают protected actions, сначала проверяется ожидаемая полезность и бюджет снабжения. Старое имущество после успешной смены идёт в общий surplus pipeline. Нет бесконечного equip/unequip, buy/sell ping-pong и продажи последнего подходящего оружия. Ошибка маршрута ведёт к альтернативному источнику/ограниченному retry, не проверке всех тренеров/спотов.

## E. Цены и инструмент Alt+B

Общий valuation используется phantom bid/ask/manufacture и offline catalog; расширить existing rate-aware sources/recipe expected costs, не заменить всё `price*x10`. Учитывать **реальный** loot chance и quantity, Adena доход, NPC buy/sell/tax, рецепты/неудачи, расходники, редкость/применение, тип/грейд/улучшение и настраиваемое целевое время накопления. XP/SP rates не становятся механическим множителем цены. Обнаружить actual Alt+B bypass→списки/мультиселлы и трогать только этот reachable набор, не все XML.

Доставить работающий PowerShell/CLI `Plan / Apply / Rollback` (предлагаемый путь `tools/phantom-economy/Price-PhantomEconomy.ps1`, при существующем аналоге расширить его). Inputs: rates snapshot, target-time/scarcity profile, реальные item/recipe/shop facts. Plan по умолчанию read-only, выдаёт компактные JSON/TSV diff+reason+source hash и список UNPRICED; одинаковые inputs дают тот же план. Apply требует конкретный проверенный plan/hash/root, делает backup изменяемых файлов, проверяет preimage, атомарно применяет только разрешённые цены; Rollback адресный и не затирает более поздние чужие правки. В own candidate автоматическое Apply уже разрешено AUTHORITY; на пользовательской живой поставке здесь не применять.

Не отключать неизвестные ограничения multisell, не переводить другие валюты в Adena без модели. Не менять базовые combat/drop rates ради демонстрации. Сформировать примерные x10/x20 расчёты без запуска серверов, но в candidate применить только один согласованный профиль на фактических rates **до** measurement; это стартовый баланс, не гарантия идеальной экономики.

Защита от бесконечного арбитража: для поддержанных цепочек NPC/Alt+B→private bid, craft→sale и crystalize→sale учитывать входы, fees, stochastic yield, rounding/MaxAdena. Нельзя доходным считать closed buy/convert/sell cycle без внешнего ресурса/времени/лимита. Data graph bounded; нет перебора всех возможных путей H5. Непроанализированный маршрут помечать, не заявлять «арбитраж математически невозможен везде». Эпики оцениваются отдельной редкой категорией выше обычной S/S80 бижутерии по настраиваемому premium, не по одному грейду.

## G. Личный solo Rift — разрешён необходимый lifecycle scope

Повторно прочитать только `RIFT_ANALYSIS067.md` и названные методы. Теперь разрешено устранить установленные причины: owner-checked room reservation, сериализованный/idempotent terminal state и timer callbacks, death/restart-point exit hook. Это не новая система инстансов. В отличие от067, scope **не ограничен одной строкой min-party/singleton**; нужные изменения Manager/DimensionalRift/Party/Player/RequestRestartPoint допустимы.

Персональная льгота только через существующий personal allowlist, exact access0 и исключение Phantom/headless; default OFF, только отсутствие/minimum Party. При solo возможен внутренний настоящий singleton Party, если native это требует: создать после revalidation, провести native fee, при неудаче компенсация по факту, завершить и распустить **только созданный этой операцией** singleton. Не распускать выросшую/чужую Party; pending invitation revalidation обязательна. При существующей Party сохранить native leader/max/fees/eligibility/world identity.
