# PHANTOM-WORLD-COORDINATION-130 — единая архитектурная реконструкция

**Статус:** READY_FOR_CODEX (НЕ реализована и не протестирована). **Дата подготовки:** 2026-11-06. Принятый продуктовый контракт: `reference/ARCHITECTURE-CONTRACT-002.md`; в случае несоответствия проверить source и уточнить существенный компромисс у владельца, не делать вид, что проект документа уже является исполняемой системой.

## Исходная проблема

TASK126–129 доказали разные native элементы Solo/Party/PvP, но упёрлись в взаимные fences Schedule/Presence/Ecology/Background/Materialization/Party/Supply/Travel, не дав устойчивую автономную Party. TASK129=PAUSED, FULL=NO после ~18 часов; 12 commits (28 files) содержат полезные preferences, CAS offers, human-follow и bugs, НО F1–F9. Главная ошибка F1: поиск строится на materializedFarmMembers, `Participant` требует objectId+epoch, поэтому 5000 durable персонажей не могут социально объединяться без World Player. Тесты и stage слишком дорогие, граничные контрактные ошибки выявляются только после многочасового GameServer.

## Зачем эта цельная задача

Изменить зависимость между системами: **долговечный профиль → текущее намерение → логическая группа/фоновая деятельность → управляемая потребность в физическом Player → законный native-сеанс → безопасный BACKGROUND**, а не «сначала World Player, потом можно решить объединиться». Не переписывать готовый L2J. Все изменения — единая причина/результат; не создавать TASK130-A/B/C или новую номерную задачу на каждое исправление.

## Обязательные продуктовые свойства (в одной реализации)

**1. Intent и единые переходы.** Существующие GoalStore/Decision Engine — source of truth. В текущем состоянии есть bounded goalId/revision, owner, priority, deadline, outcome, retryAt/reason; явные `COMPLETED`, `YIELD_ACCEPTED`, `WAIT_UNTIL`, `REPLAN`, `REJECTED`. Никакой глобальной второй state machine поверх существующей. При Party/Commerce/Supply/Combat/Store и смене lifetime — только type-specific законный handoff, ресурсный owner не исчезает из-за приоритета Party.

**2. Presence/Population.** `READY/ACTIVE` планировщика, `materialized in World`, `native offline merchant`, `human Player` — четыре разных понятия. Чёткие источники: durable=5000; target logical admitted=128; target actual managed physical=128 при наличии допустимой ёмкости/политики; 250+ отдельные offline stores, НЕ занимающие permits PhantomMaterializationService, но учитываемые в нагрузке World. Реальный physical target может быть достигнут ambient demand без человека — не создавать только 7 Player при доступных 128 slots и отсутствии иных blockers. Human locality приоритетна, но не единственная причина материализации. При недостижении цели показать количественный `reason`, не печатать фиктивные 128.

**3. Background.** Законная долговременная жизнь профиля и логической Party при нуле native Player. Существующие Background/History осуществляют time/EXP/SP/items только в рамках авторитетных state/ledger/policy; no double reward между background и native, strict receipts/expectedHash/epochs, отказ на конфликт. Общая цель/геопозиция/социальные связи группы сохраняются при restart и переходе foreground→background. Логическое согласие не делает фантомов мгновенно членами stock Party.

**4. Materialization.** Одна authority для физического `Player` и native epoch. Обрабатывает typed demands (наблюдение человека; ambient target; группа; принятое путешествие; native context) через один согласованный admission с Presence/Background/Ownership/Capacity. Важна **разная семантика прав**: LOGICAL_PARTY_WAKE не имеет чужих acceptedJourney/soft reclaim прав. Есть finite WAIT + retryAt/causal trigger. Одно материализованное звено логической Party может запросить bounded wake товарищей; остальные не обязаны одновременно материализоваться. При уходе наблюдателей — grace + сохранение и безопасная дематериализация группы без ухода прямо из видимости, боя, CAST/STORE, native Party c реальным игроком или in-flight. Один groupId остаётся сквозным, новая physical session имеет новый epoch. Канонический location/Geo/GK не обходить.

**5. Party.** Durable LogicalParty 2–9, key `groupId+generation` и `profileId`, без обязательного objectId/epoch; роли, leader profileId, objective, background cursor, version. Участники выбираются из bounded/paged eligible durable, даже если 0 World Player; 0/20/35/50/80% stable preference из уже существующего WIP129 `PartySeekingSettings`. `1–39=0%` запрещает самостоятельный поиск, не штатное приглашение человека. Состав без обязательного хилера, но соответствующий миссии; собрать пару возможно. Group aggregate commit и CAS identity reservation, exactly-one-current-group; failed partial saga компенсируется. Recovery по durable group records, НЕ materialized page. Native Party создаётся stock invite/accept только после законной физической встречи, соблюдения Geo и текущих ролей. В mixed Party following за человеком при единственном human/достоверном owner, но official Party/Clan Leader не подменяется. Олимпиада выводит конкретного участника из Party, не из клана.

**6. Scheduler/Navigation.** Один существующий общий `PhantomScheduler`, ограниченные batches/fair cursors/event triggers. WAIT с кодом причины/nextDue, нет per-pulse полного SQL поиска по 5000, retry storm, молчаливого catch{return false}. Пункты F2/F3/F6: не выбирать top4 anchors/top15 actors ДО проверки годности; bounded paging и fairness, различать `UNKNOWN`/`TEMP_BLOCKED`/`UNREACHABLE`, штатный WALK ingress + route planner, healer должен иметь безопасный маршрут, не обязательную Solo DD combat feasibility. Ни второй AI, ни второй Nav/Geo/Combat engine.

**7. Instrumentation.** Один компактный диагностический snapshot на профиле/группе и общие counters: durable, scheduledEligible, presenceAdmitted, logicalParty, materializedManaged, physicalTarget, physicalCap, pending/deniedByReason, nativeOfflineMerchant, humanOnline, worldTotal, recent useful actions. Count source из реального мира, offline traders disjoint от managed. История последнего meaningful action и last wait reason. Строго не модифицировать stock Heal ради доказательства теста без явной технической необходимости.

## Локальная и реальная приёмка

Дешёвая компактная постоянно используемая test boundary проверяет: 3 durable профиля (0 materialized) договариваются и сохраняют LogicalParty; при simulated process restart логическая группа осталась; второе предложение отклонено; paging 5-й anchor/16-й candidate; typed admission и отказ; ambient target учитывает реальную physical capacity; группа после fake native boundary без потери membership возвращается в Background; double settlement prevented. **Нельзя** считать fake portal/native substitute доказательством GameServer.

Один ограниченный реальный GameServer smoke после прохождения дешёвых проверок: groupId из логических профилей → настоящий materialized member → bounded wake второго/третьего → native stock Party invite/accept → полезный групповой PvE с настоящим reward → normal STORE → sameDB/sameJAR restart → продолжение полезной деятельности. Group background/foreground transition и вывод физически видимых materialized counters. Heal — если в группе подходящий learned healer/естественно раненый союзник, проверить настоящий cast+HP/MP; иначе `HEAL_NOT_PROVEN`, не выдумывать лечение. Желаемая ultimate FULL — см. ACCEPTANCE.md; не требовать production клановых войн и Олимпиады как текущий FULL gate.

## Производительность и итог

Никаких новых 35–90GB stage/preimages/архивов. Один lightweight immutable clone, реиспользуемый sandbox и scoped evidence; не создавать zip самого codebase. Локальные проверки как правило <=5 минут; full-native загрузка больше 5 минут возможна и не означает автоматического дефекта, но каждый новый запуск основан на *новой* проверенной причине. Если повторный прогон без causally changed code/conditions — остановить native lane и диагностировать контракт дешевле. Никаких новых десятков однократных scripts только для review. Сравнить полезное code-change/время-токены с overhead. Без остановки ради произвольного лимита времени, но с окончанием дорогих no-progress loops.
