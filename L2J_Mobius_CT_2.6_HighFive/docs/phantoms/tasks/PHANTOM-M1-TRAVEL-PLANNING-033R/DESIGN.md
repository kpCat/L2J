# Решение координатора: стратегия отдельно от локального исполнения

## 1. Что означает рисунок пользователя
«БОТ» — actual Player, «ФАРМ» — область полезной работы, зелёные точки — узлы,
красная линия — желаемый обход, синие — рассмотренные неудачные связи, чёрные
треугольники — препятствия. Рисунок не содержит реальных координат и не доказывает
геометрию Talking Island. Его переводим в регрессионный сценарий с обходом.

Цель — FARM_AREA с условиями уровня/ресурсов; mob objectId временный. Цель маршрута
может быть допустимой точкой входа в область, а не её единственным геометрическим
центром. Изменение farm goal проходит existing atomic publication, не запись через debugger.

## 2. Существующие роли сохраняются
PhantomHistoricalBackgroundPlanner/Service выбирают/публикуют farm-план.
PhantomVisibleFarmTravel владеет journey, actual MOVE и final arrival.
PhantomNavigationService ограничивает очередь/поиск; L2jNavigationBackend вызывает
stock PathFinding; NodeBuffer уже содержит A*. GeoEngine/doors/water — источник
геометрической допустимости. NormalGatekeeperTravel содержит макрорёбра и stock
NORMAL GK executor уже присутствует в VisibleFarmTravel.

Добавляются только недостающие контракты: TravelStrategy (выбор способа/стоимости)
и при необходимости BoundedWalkCorridor (граф проверенных коротких native-коридоров).
Они не выдают EXP, не двигают Player, не владеют saved background state.

## 3. Необходимое отличие от старого033
Нельзя строить все промежуточные пункты формулой current + unit(goal-current)*2000.
Точки-кандидаты могут быть предложены, но ребром становятся ТОЛЬКО после native
findPath + strict segment/height/door/water проверки. Нужно хранить alternatives,
включая боковой ход и временное удаление от цели. Движение не начинается по одному
доказанному первому участку, если никакого плана продолжения нет.

Сначала пробовать уже имеющийся stock путь до допустимого goal-point. Если query
выходит за локальный buffer, выбирать макрокоридор через existing topology/portals
или ограниченный локальный overlay подтверждённых native routes. BACKGROUND edge
макрографа — только предложение; он не разрешает физический WALK.
Общий путь можно уточнять по ходу, но каждый отправляемый native leg уже проверен;
после изменения двери/цели следующий участок перепроверяется. Существование пути
на момент расчёта не гарантирует навсегда проходимость в динамическом мире.

## 4. Граф и ограничения
Node identity включает instanceId, фактические XY/Z и поверхность/геослой, если он
доступен. Один XY на мосту и под мостом — не один узел. Нельзя сливать разные Z
по близости XY. Рёбра направленные; A→B не доказывает B→A. Для требуемого roundtrip
доказывать оба направления отдельно. Не вводить универсальный slope-angle вместо
stock NSWE/height/door predicate.

Проверенный коридор сохраняет все повороты, необходимые для обхода. Сглаживание
разрешено только после проверки нового длинного ребра, включая промежуточную воду.
Больше waypoints не значит умнее: контроллер отправляет следующий нужный поворот,
а не дёргает MOVE_TO каждый tick. Не применять случайный jitter возле стен.

Overlay строится demand-driven вокруг actual позиции/планируемой области, НЕ для
всего мира/1280background actors каждый tick. Предлагаемый структурный бюджет
одной операции:<=128 узлов,<=512 кандидатных рёбер,<=32 stock path queries,
<=4096 поисковых меток. Это новые limits КООРДИНАТОРА поиска, не повышение stock
buffer/waypoints/deadline. Реальное ограничение существующего request/attempt имеет
приоритет. Поиск выполняется порциями существующим navigation executor (max2),
без ожидания других worker под Player/owner/DB/global lock. Deadline/cancellation
проверять между native calls; закончился бюджет — SEARCH_LIMIT, не UNREACHABLE.
Кэш ограничен и привязан к instance/геометрии/точкам; запрет участка не мигрирует
на чужой epoch. Unknown edge не равен свободному проходу.

## 5. Выбор WALK vs транспорт
Сравниваются полные допустимые планы: пешая длина/текущая native скорость +
ожидание/каст возврата + подход к реальному GK + actual teleport delay + последний WALK.
Деньги/scroll counts — ограничения всего плана, не каждого ребра отдельно.
Сначала безопасность/доступность, затем ожидаемое время, затем расход и стабильный tie-break.
Не оценивать выигрыш по евклидову расстоянию и не называть решение глобальным optimum
по всей карте: это минимум среди проверенных кандидатов.

NormalGatekeeperTravel.search сейчас BFS по числу рёбер; это НЕ «самый быстрый путь».
Старую семантику background callers не менять молча: добавить явный weighted query
для новой стратегии либо сравнивать complete route candidates новым selector.
Если в графе присутствуют телепорты, евклидова эвристика времени может завышать
истинную стоимость; использовать Dijkstra/h=0 либо доказанную нижнюю оценку.
proposals/ содержит bounded resource-aware Dijkstra как справочный алгоритм.

## 6. Недоступная цель и отсутствие наблюдателя
После конечного route failure отменить своё незавершённое движение/hold, сохранить
точный failure witness и через existing plan publication выбрать достижимую цель.
Не делать новый goal только для сброса debt/deadline. Нет подходящей локальной
цели — оценить доказанный transport, а не снижать требования по level.
При уходе REAL новые actions прекращаются по текущей retention policy; earned work
завершается; valid background transition использует actual сохранённое состояние.
Ретрай маршрута не должен бессрочно удерживать actor материализованным.

## 7. Не создаём невозможные обещания
Фактических клиентских mesh у этого слоя нет. Он знает препятствия, присутствующие
в geodata/doors/zones. Неполную geodata не лечить randomTeleport. Узкая пещера,
многоярусный этаж или динамическая дверь требуют отдельного реального геосвидетельства.
NO_ROUTE_WITHIN_BUDGET честен; permanent idle после такого отказа — не успешное поведение.
