# Практическая производительность модели 4–8 МиБ

Пользователь: i7-11850H / 128 GiB RAM / NVIDIA RTX A5000 16GB; игровой JVM с 128+ видимыми фантомами — критический budget. Вес в мегабайтах не равен силе модели. При ~8 МиБ float32 ≈2.1 млн параметров; наивно применять эту сеть заново к 16 навыкам каждого фантома = дорого. Требование: закодировать состояние один раз, ранжировать действия дешёвой «головой», бюджеты per actor и per pulse; действительное количество вызовов зависит от combat events, а не от числа 5000 профилей.

Отчёт Bench: 128 logical actors, 4/8/16 предлагаемых действий, warmup+фиксированная длительность; p50/p95/p99, allocation, CPU; отдельное snapshot collection, entity encoder, action scorer, owner dispatch, OFF/SHADOW/ON; latency указывают на фактических тестовых данных. Не смешивать 7.3 µs V1 на готовых векторах с полной V3 стоимостью. Сравнить CPU по snapshots и снять ограничения запуска, когда данные пусты.

Цель: разумный p95 полного выбора <3–5ms для rare decisions без постоянной задержки боя, с деградацией на stock при бюджетном превышении; если превышена, сперва снизить частоту/ширину/отсев, не перекладывать каждую decision на GPU. Не нагружать Graphics CUDA/driver в game hot path. На RTX A5000 в LEARNING-004 возможен отдельный GPU batch trainer и distillation. Перенос веса в GPU не экономит CPU игры, если native world и JVM остаются там же. Измерить VRAM/скорость только когда GPU trainer действительно создан, не писать фиктивные GPU цифры.

Глобальный модельный объект 1 shared per JVM; per-actor — state descriptor/history, с bounded hot allocations; запрет синхронной SQL и новых per-profile Threads. 5000 persistent профилей нематериализованных не обязаны постоянно проходить V3.
