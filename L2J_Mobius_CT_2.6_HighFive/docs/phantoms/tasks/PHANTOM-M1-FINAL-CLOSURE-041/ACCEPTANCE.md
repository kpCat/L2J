## Применимость старого PASS

040 — baseline, не автоматический final041 PASS. Для нового semantic candidate повторить конечные gameplay/native gates. При doc-only публикации JAR не пересобирать; report SHA отличается от CODE_COMMIT законно. Test/tool-only изменение, не затрагивающее product JAR/game policy, имеет собственный hash и требует затронутой проверки, а не фиктивной новой игры.

Historical/negative/invalid episodes указываются отдельно с причиной. Новый run без изменившейся проверяемой гипотезы/исправления не стирает старый FAIL. Необходимые score thresholds, identity, conservation и actual-clock требования сохраняются.

## Статусы — обязательная таблица переходов

| Условие | TASK_RESULT | M1 | READY_FOR_M2 |
|---|---|---|---|
| Исполнение продолжается | IN_PROGRESS | OPEN | false |
| Любой серверный gate/R1 не PASS | PARTIAL_VERIFIED / FAILED_CURRENT_GATE / BLOCKED_INPUT_SAFETY | OPEN | false |
| Все серверные gates/O_SERVER/R1 PASS, личная проверка ещё не завершена | M1_SERVER_READY | WAITING_REAL_FINAL | false |
| Все предыдущие + O_REAL/REAL_FINAL PASS + USER_ACCEPTANCE явно дан | M1_CLOSED | CLOSED | true |

READY_FOR_PREVIEW допускается для здорового runtime с неполным gate, но не считается финальной сдачей. Эта задача не должна останавливаться на preview при исправимой причине и оставшемся бюджете. «Пользователь разрешил crash» — authority, не результат G6.

Старый Zariche incident040 не исправлен и остаётся DEFERRED_BY_USER. Он исключён из текущей ordinary acceptance по прямому решению пользователя; запись FAIL_INCIDENT_DEFERRED040 не изменяется. Новая REAL_FINAL041 может пройти без Zariche. Другой зависший обычный cast/управление или побочный эффект Phantom системы этим исключением не покрыт.

Статус-файл не статическая ложная строка: RUNNING/observerCurrent берутся из current runtime; M1/REAL_FINAL — из актуального результата с timestamp/candidate либо честно UNKNOWN. Наличие STATE=RUNNING никогда не означает CLOSED.

## Завершающая граница

После M1_CLOSED не выполнять М2. Опубликовать итог и дать точную фразу «М1 закрыт, готово к постановке М2» только при выполнении таблицы. Пользователь передаёт review ассистенту; дальнейшая задачаМ2 выдаётся отдельно после проверки результата. Все useful changes уже должны лежать в ветке и обычной поставке, не ждать будущего восстановления из локальногоZIP.
