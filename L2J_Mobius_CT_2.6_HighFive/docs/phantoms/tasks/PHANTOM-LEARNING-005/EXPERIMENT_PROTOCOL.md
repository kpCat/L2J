# EXPERIMENT_PROTOCOL — независимые парные игровые испытания

## Что является парой
Две **отдельные** реальные попытки A=stock и B=learned, имеющие один `pairId`, `scenarioFingerprint`, проверенные pre-CUT параметры (класс/level, изученные skills, экипировка, weapon enchant, броня, бижа, buffs, стартовые HP/MP/CP, уровни/тип NPC, гео/LOS, party roles, цель/таймаут/конфиг/rates), `seed`, порядок arm, ID собственных персонажей и independent spawn epochs. Сравнивать физические условия, а не только названия сценариев. Никакого повторного использования умершего/уже побитого target без нового честного spawn. Не смешивать выборки из чужих игр.

Точные исходные параметры каждый раз читаются native. Уровни/skills/items выбираются только из доступного канонического game data. Сравнения по классу/численности Party и gear держать равными внутри пары; изменять между парами. Не объявлять 61-lvl archer эквивалентом 68-lvl mage. Здесь тренируются существующие Solo/Party PvE Archmage94 и поддержка Cardinal97/EvaSaint105, без PvP.

## Допустимый pre-CUT
До начала боя TEST вправе создать fresh actor с подтверждённым equip/skills и исходным HP/MP, подготовить группу и выбрать легальную точку. После CUT эффекты, расходы, касты, урон, убийства, остановки — только штатный GameServer. Не подменять результаты SETTLE, не откатывать GameServer/SQL посреди эпизода, не использовать `setCurrentHp()` как учебный результат. Recovery лечением REST, если нужно, учитывать отдельно и одинаково в arms.

## Выбор сценариев и последовательность
1. Preflight legality, готовность Skill/КД и наличие ≥2 законных альтернатив в момент решения. Для HEAL только допустимые неэкстренные ситуации в Party, в которых stock разрешает выбор V3; emergency stock НЕ менять.
2. Новый catalog идей создаётся **алгоритмом**, не ручным списком 200 боёв. Планировать минимум 4 честных завершённых paired observations для SOLO_DAMAGE_V1 и 4 для PARTY_HEAL_V3, с минимум 2 разных фактических ситуаций и 2 разных физических actor incarnations на mode. Это минимальный функциональный smoke, НЕ мощность для доказательства преимуществ.
3. Порядок A→B и B→A уравновешивать с фиксированным seed; случайности native damage/heal/crit/aggro остаются настоящими. Один matched seed не делает случайные исходы идентичными. Сохранять невыровненные условия и отказывать сопоставлению с причиной.
4. Для каждого mode предусмотреть как минимум **одно доказанное действие, где B выбрала другой готовый skill/target и он реально исполнился**. Отсутствие таких действий — `NO_POLICY_DIVERGENCE`, а не «обученная модель равна stock». Можно выбирать новые **законные** условия, но не заставлять нейросеть искусственно поменять решение.
5. Timeout, pre-CUT SKIP, бой без target, stale actor, 0 tracked effect, смерть и abort входят в ledger с реальной причиной и в анализ попыток; **не выбрасывать неудачи ради красивого success rate**. Для пары без равных pre-CUT факторов status `UNMATCHED`; не зачислять её в fair sample.

## Повторы и разброс
Все stochastic outcomes native. Нельзя синхронизировать crit через подсунутый mock/forced RNG или объявлять два отдельных боя «побайтно одинаковыми». Для оценки влияния политики нужны повторения, balanced order и интервалы неопределённости. Если ожидаемый effect небольшой, 4 пары дают только smoke — расширение после задачи может быть на 20/50/100 пар и последующие ночи.

## Приёмка кампании
Если не удалось получить 4/4 valid pairs из-за реальных законных ограничений — честный PARTIAL + разбор отказов и следующее безопасное действие. Не снижать требование без согласования, не подменять боевую сессию replay-видео или локальной математикой.
