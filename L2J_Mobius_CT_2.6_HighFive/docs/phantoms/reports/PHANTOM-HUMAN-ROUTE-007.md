# PHANTOM-HUMAN-ROUTE-007 — запись маршрута владельца

Статус `PARTIAL`. Сборка, адресные автоматические проверки и тест закрытого Windows-канала прошли. Для игровой приёмки нужны согласованная активация, штатная высадка с реальным клиентом, физический проход и переход ко второй сцене. Живых проходов в этой работе не было. Native WALK фантома и `PROVEN` не подтверждены.

## Реализация

- `HumanRouteService` запускается только с явным JVM-параметром и приватным `EnableHumanRouteDemonstration=True`. Привязывает один обычный `Player`, objectId, аккаунт, тот же `GameClient`, инкарнацию GS и срок согласия. Переход к следующей сцене требует квитанцию предыдущей. `stop`, потеря клиента, смерть, неожиданный телепорт, другая instance и потеря операторского допуска прекращают цепочку.
- `HumanRouteMailbox` проверяет owner-only Windows ACL, канонические пути, один writer lock, инкарнацию, очередь запросов, ID и срок. Отдельный приоритетный `stop` отменяет ещё не выданный телепорт. Канал локальный, без TCP и общих команд `LocalPlayPilot`.
- `HumanRouteScenes` сверяет контрольную сумму снимка learned, отпечаток GeoData и точное направленное ребро с отказом. Очередь ограничена восемью сценами. Отсутствующий ориентир даёт `NEEDS_LANDMARK`. Старт проходит проверку поверхности, воды, ограниченных зон и сухих выходов. Запись начинается после проверки штатной высадки.
- `HumanRouteTrace` различает стартовый телепорт, серверные выборки с частотой до 4 Гц, паузы, возврат к началу, WaterZone, изменения поверхности и разрывы. Сохранение атомарное, `.partial` остаётся незаверённым при обрыве процесса. Для `ARRIVED` нужны штатное обновление движения в целевой геозоне и согласующаяся с ним конечная позиция игрока. При промахе сохраняется `PARTIAL/NOT_REACHED`.
- `HumanRouteHint.readWalkCandidate` читает целый экспорт `ARRIVED` с тем же отпечатком GeoData как подсказку. Проверяет сухие точки и штатные линии WALK. Мокрые или разорванные записи остаются свидетельствами для разбора. Сервис не вызывает writer `PhantomRouteLearning` и не создаёт native-квитанций.

## Bounded writer audit

Игровые writers положения и lifecycle остаются штатными. `Creature` сообщает о начале телепорта, подтверждённом игровом изменении позиции и смерти, `WorldObject` о смене instance, `GameClient` о разрыве, `WaterZone` о входе и выходе. Они помечают только текущую разрешённую сессию в памяти и не открывают файлов. `GameServer` подключает сервис, `Shutdown` отзывает привязку и завершает ограниченную запись до остановки пулов. При изменении поколения GeoEngine запись прерывается. Явное состояние `TELEPORT_PENDING` и проверка фактической высадки защищают от зачёта стартового перемещения.

Единственный writer экспорта — операторская задача общего планировщика GameServer. Размер сцены до 2 400 выборок, до 512 событий воды и до десяти минут. Разрешение на одного клиента ограничено 45 минутами и временем приватного permit. Экспорт находится в закрытом каталоге вне Git. Сырые перемещения, личность аккаунта и служебные параметры не попадают в ответ оператору. Записи чата, IP, паролей, пакетов и SQL нет. Проверка каталога и атомарная публикация выполняются вне игрового потока. Native learned manager, Geo Trainer, навигационный движок и фоновые writers 006 остались прежними.

## Порядок работы Codex после допуска

1. Согласовать с владельцем одно окно активации и один выделенный персонаж с `accessLevel=0`. На Bartz перед любым действием сверить SHA поставки и хэш JAR, живые PID GS/LS, порты, ночное окно, архив конфигов и подтверждение штатного STORE. Выделенный персонаж может быть существующим. Новый создаётся только с разрешения через штатный Account Manager, пароль владелец вводит локально.
2. Из фактических отказов собрать короткий снимок одного–четырёх подходящих `region-*.tsv` из обычного learned-каталога. Сохранять исходные байты и хэш каждого снимка. В приватный `scenes.tsv` поместить до восьми строк с точными направленными рёбрами. Поля разделены табуляцией в порядке `id`, `startX`, `startY`, `startZ`, `targetX`, `targetY`, `targetZ`, `radius`, `heightTolerance`, `startLandmark`, `directions`, `LEARNED_FAILURE`. Ориентиры подтвердить по игровым данным. Для неизвестного ориентира оставить `-`, чтобы исключить сцену из переноса. Записи из 006 относятся к своим снимкам и требуют проверки на актуальной геодате.
3. `tools/phantom-local-play/HumanRoute-007.ps1 -Initialize -Root <private-root> -TestAccount <login> -ObjectId <id> -ScenarioFile <file> -FailureSnapshot <directory>` создаёт новый каталог непосредственно под `%LOCALAPPDATA%\PhantomHumanRoutes`. Разрешение по умолчанию истекает через 45 минут. При запуске согласованного GS передать JVM `-Dphantom.humanRoute.root=<private-root>` до `-jar`. Параметр и permit относятся только к этому запуску. Проверки загрузки должны дать operator status с соответствующей инкарнацией. Для отката отозвать permit, снять JVM-параметр при следующем согласованном запуске и сохранить приватные квитанции для разбора. Писать в live learned/SQL не требуется.
4. Для действий Codex использует тот же скрипт с `-Root <private-root> -ServerProcessId <verified-gs-pid> -Action <action>`. Для `arrived`, `skip` и `next` добавляет `-Scene <scene-from-receipt>`. При отсутствии квитанции проверить `status` перед повтором. Команды и координаты остаются внутри операторского контура.

| Слова владельца | Действие Codex |
|---|---|
| «зашёл» | `arm`. Сообщить об отсутствии персонажа или дождаться `RECORDING`. Назвать ориентир старта и цель из квитанции. |
| «дошёл» | `arrived` с ID текущей сцены. Сообщить статус, число точек и факт наблюдения воды. При `SEALED`, действующем согласии и ещё одной сцене выполнить `next` с ID сохранённой сцены. Дать новый ориентир после `RECORDING`. |
| «пропустить» | `skip` с ID текущей сцены. После сохранённого `SKIPPED` взять следующую сцену с `next`. |
| «стоп» | `stop`. Дождаться терминальной квитанции с числом сохранённых эпизодов. |
| «проверить» / «продолжить» | `status`. При «продолжить» использовать `next` только для последней `SEALED` или `SKIPPED` сцены. При завершённой сессии сообщить результат. |

Для native-приёмки открыть заверённую подсказку отдельно. `PROVEN` возможен только после самостоятельного WALK обычного фантома и его native-квитанции. Manual gate остаётся `REQUIRED`.

Ветка `feature/phantom-world`, проверенный исходный SHA `36e2bbf6a018c28efe825e0a8bcf7e7588102aef`. Точный список файлов проверяется перед коммитом. Итоговые SHA коммита и результат обычного push фиксируются внешней квитанцией после публикации.
