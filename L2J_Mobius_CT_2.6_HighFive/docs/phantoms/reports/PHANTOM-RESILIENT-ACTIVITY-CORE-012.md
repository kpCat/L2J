## Изменения

| Файл | Что изменено |
| --- | --- |
| `PhantomSystem.java` | Дожидается принятых операций и освобождает независимых native owners перед обработкой terminal recovery failure. Повтор STOP после истечения `WAIT_ACCEPTED_CONTROL` продолжает ту же фазу с закрытым допуском. Неопределённый STORE оставляет экземпляр доступным для диагностики и блокирует выход. Пост-STORE readmission разрешён только в RUNNING. |
| `background/PhantomBackgroundService.java` | В STOPPING сохраняется завершение принятого STORE, а recovery без своего native owner откладывает новую материализацию. Результат подтверждённого STORE при последующем `CATCHUP_FENCED` сохраняет поведение 011. |
| `pvp/PhantomPvpService.java`, `PhantomSystem.java` | Источник `ACTUAL_ATTACK` использует допуск ambient/foreground обычного фарма даже без наблюдателя. Существующий PvP hold закрывает новые farm roots, а маршрут и PvE yield проверяются независимо в одном pulse. Действующие проверки SOLO, принятых journeys, pending STORE и party остаются в цепочке допуска. |
| `background/PhantomVisibleFarmTravel.java` | Перед `MOVE_TO` сверяются текущий допуск и запись маршрута. Удалённый маршрут перестаёт проходить `currentJourney()` даже при совпадении цели и epoch. Текущий эффект STORE сверяется обычным владельцем. |
| `PhantomSystem.java` | При публикации нового root для того же SOLO owner подготовка ждёт native attack/cast/loot boundary без льготного окна на завершение PvE-цели. Durable checkpoint, CAS, companions и настоящая передача SOLO↔PARTY используют существующий путь. |
| `test/.../player/PhantomShutdown103Checks.java` | `--stop012` воспроизводит ранний отказ из background recovery. Фикстура проверяет ожидание принятых операций, истечение бюджета, повтор STOP, освобождение других акторов и сохранение неопределённого результата. `--stop121` проверяет тот же контракт для ordinary death recovery. |

В 011 уже разделены подтверждённый STORE и отказ следующего допуска. Отдельная причина удержанных владельцев была в `WAIT_ACCEPTED_CONTROL`: первый recovery failure прерывал STOP до проверки quiescence, а повтор оставался в FAILED. Кандидат даёт штатному дренажу завершиться и сохраняет отказ для неопределённого эффекта. Тест просроченной фазы моделирует разрешившуюся занятость и не использует SQL или живой World.

`PhantomExecutionControlPort.onPulse()` по-прежнему использует `goal.*` publication как запрос с durable checkpoint, даже при одинаковых owner и recipient. В `PhantomSystem.executionCheckpoint()` этот checkpoint атомарно согласует компоненты root, дочерние намерения и native receipt. Для дальнейшего сокращения зависимостей нужно доказать, какие компоненты можно исключить из атомарной публикации. В 012 сокращено ожидание PvE-цели в `prepareExecutionOwner()`. Транзитная PvP-реакция использует текущего игрока и не публикует новый root.

## Что остаётся открытым

Приёмка Bartz требует отдельного согласованного окна после закрытия кодовых gates. Проверки L4/L5 из 011 тоже открыты — два причинно подтверждённых цикла обычного фарма и завершённый межрегиональный WALK. Полноценные дальние маршруты требуют связности и проверки бюджетов на уровне всей поездки. У партий остаётся отдельная проверка native handoff. Олимпиада, ТВ и осады требуют собственных игровых кандидатов и фактической приёмки.

Для связанной проверки G3 нужна готовая изолированная native TEST-среда с обычным фармом через production `PhantomSystem`. `PhantomPvp074Native` и `PhantomCombat131DuelRuntime` поднимают отдельный `PhantomPvpService` без production callback `preparePvpFarmYield`. `PhantomFarmRouteRecovery006Native` ожидает точную подготовленную среду TASK130, которой нет в checkout. Эти пути сами по себе не покрывают требуемый переход `WALK/PvE → ACTUAL_ATTACK → engage/retreat → replan`.
