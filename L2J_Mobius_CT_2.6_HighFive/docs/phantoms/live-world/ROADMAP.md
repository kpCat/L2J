## LIVE-001 — стабильность запуска и доступность уже обещанного QoL

### Вход

Текущий пользовательский runtime, сведения об исчезновении процесса/дисконнекте и реальные логи. Июльский `Access denied` LoginServer не считается причиной сентябрьского события. Сначала использовать `CRASH_CHECK.md`; до получения свидетельств корневая причина — `UNKNOWN`.

### Файлы для точечного чтения/изменения

- `tools/phantom-local-play/Start-LocalPlay.ps1`, `Stop-LocalPlay.ps1`, `Check-LocalPlay.ps1`.
- `tools/phantom-local-play/Build-LocalPlay.ps1` — только доставка/сохранение пользовательских настроек; НЕ запускать пересборку runtime поверх игры.
- Runtime-копии этих скриптов и `game/java.cfg`, `login/java.cfg`, `local-play.json` — сначала сравнить и сохранить исходное состояние.
- `java/org/l2jmobius/gameserver/qol/PersonalCharacterQoLService.java`.
- `dist/game/data/scripts/handlers/bypass/npc/SkillList.java`.
- `java/org/l2jmobius/gameserver/model/actor/instance/Folk.java`; `Npc.java` и конкретный trainer script — только если трассировка туда приводит.
- `game/config/Custom/PersonalCharacterQoL.ini`, `CommunityBoard.ini` фактически используемого runtime; одноимённые source-конфиги не выдавать за фактически загруженные.

### Контрольная точка 001-A: доказательства вылета

1. Записать дату/часовой пояс, реальные Java PID, start time, executable, command line, слушающие порты и runtime PID records.
2. Снять полные имена и хвосты всех недавно изменённых непустых логов, включая rotating/console/packet файлы, не только строки `ERROR`.
3. Развести случаи: Java завершилась; Java работает, но не отвечает; Java/порт работают и отключился только клиент; штатный stop/restart; процесс исчез по внешней причине.
4. Проверить stdout/stderr, crash file в runtime и `%TMP%`/`%TEMP%`, Windows Application/System на точное время. Ошибку чтения журнала не подменять «событий нет».
5. Сопоставить маршруту Talking Island точное время события. Само совпадение с границей города не доказывает ошибку geodata.

**Выход 001-A:** короткий отчёт с доказанной категорией либо честным `UNKNOWN + какие свидетельства отсутствуют`. Отсутствие повторного вылета не превращается в «исправлено».

### Контрольная точка 001-B: запуск больше не теряет консоль

Для каждого запуска иметь отдельный каталог с run-id и stdout/stderr для LoginServer и GameServer. Сохранять PID/start time, параметры JVM, SHA запущенных JAR, факт штатной команды stop и полученный exit code. Нельзя перезаписывать предыдущую сессию и запускать бесконечный авторестарт, скрывающий причину.

Супервизор должен действительно дождаться завершения дочернего процесса или сохранить обработчик его выхода; недостаточно подписки, которая пропадает вместе с короткоживущим PowerShell. Не менять текущую защиту от остановки чужого PID.

Диагностика JVM при следующем контролируемом запуске: `HeapDumpOnOutOfMemoryError`, `HeapDumpPath`, `ErrorFile`, ограниченный по размеру GC log. Перед dump проверить свободное место; heap dump может быть большим и содержать приватные данные. Его не загружать автоматически и не класть в Git.

**Проверки:** обычный старт/stop; ошибка старта на изолированном тестовом процессе; контролируемое завершение тестового дочернего процесса с известным exit code; повторный запуск не уничтожает прошлые файлы. Не убивать ради теста действующую игру.

### Контрольная точка 001-C: cross-class и Alt+B

Сначала подтвердить реальный account name и персональный допуск. Сценарий: real main-class `localplayer`, personal flags ON, `AltGameSkillLearn=False`. Наблюдение Nerga/Kincaid — воспроизвести как UI → handler → service → available skills → purchase → relog.

Нельзя заранее считать виноватым только начальный HTML: `Folk.showSkillList()` тоже выдаёт `showNoTeachHtml()`. Добавить узкую диагностику результата допуска и причины отказа, а не лог каждой игровой операции. Исправить доказанную точку без глобального `AltGameSkillLearn=True`.

**Приёмка:** оба наблюдённых тренера открывают допустимые foreign CLASS-деревья; доступный по уровню/условиям навык учится со штатной оплатой и сохраняется после relog; недопустимый по уровню/профессии навык не выдаётся; non-allowlisted и headless Phantom не получают личных привилегий; subclass/GM/hero/clan/special trees не расширены. Alt+B показывает личный раздел и корректный статус допуска, а не только общий Merchant.

### Запрет расширения

В LIVE-001 не менять население, экономику, мир и расписания. После исправления причины вылета повторить исходный маршрут и длительный локальный smoke; отдельно указать, что именно проверено.

## LIVE-002 — все фарм-зоны как данные, а не ручной поход по карте

### Что значит «все»

Все обычные фармовые spawn-группы, реально относящиеся к этому High Five datapack: открытый мир, все стартовые территории, mid/high level зоны, комнаты обычных Catacombs/Necropolis. Инстансы, рейды, эпики и условный/ивентовый spawn не смешиваются с обычным фоновым фармом; они получают отдельные типы и запись в реестре, а не исчезают из учёта.

### Исходники

`dist/game/data/spawns/**`, `data/stats/npcs/**`, `data/mapregion/**`, `data/teleporters/**`, `data/zones/**`, `data/instances/**`, `data/phantoms/topology/**`, `data/phantoms/knowledge/**` и соответствующие native loaders. Учитывать конфиги, фазы и условные спавны: наличие XML ещё не доказывает действующий spawn.

### Предлагаемые новые артефакты

- `tools/phantom-world-data/` — детерминированный генератор/проверка. Это новый путь, не утверждение о существующем инструменте.
- `docs/phantoms/live-world/WORLD_COVERAGE.tsv` — полный реестр, включая исключения.
- `dist/game/data/phantoms/topology/generated/` — предлагаемый раздел generated data; подключать только после проверки/расширения существующего loader.
- `WORLD_DATA_MANIFEST.json` — baseline, версии, SHA источников, счётчики и зависимости.

### Шаги

1. Один машинный обход исходников/loader-данных. Для каждой группы сохранить стабильный ключ `source + group + geometry/condition`, npc IDs, уровни, обычный дроп и spoil, количество/respawn, instance/type, этаж/Z и доступность.
2. Сформировать зону/подзону из существующих геометрий. Сильно различающиеся уровни и этажи не объединять. Не делать одну точку «центр полигона» без проверки проходимости.
3. Для каждой зоны создать точки входа, безопасные точки материализации и coarse связи: внутри района, ближайший город, штатный GK и разрешённые переходы. Стоимость и время пути берутся из действующей модели; не давать бесплатных телепортов.
4. Строить маршруты не только «старт → первый моб», но и выход со спота/обратный путь/переход к следующему диапазону уровней.
5. Для обычных Cat/Necro сохранить room/коридор/дверь/доступ. Не считать отдельный SSQ сюжетный instance покрытием всей сети катакомб.
6. Выдать статус каждой записи: `READY_STATIC`, `NEEDS_GEODATA`, `CONDITIONAL`, `INSTANCE`, `RAID`, `EXCLUDED(reason)`; затем отдельно результат проверки на реальной геодате.
7. Проверить дубликаты, отсутствующие NPC/предметы, диапазоны, этажи, ссылки маршрутов, компоненты связности и происхождение координат. Повторный генератор на тех же входах даёт те же байты.
8. Локально прогнать геодату пакетно; вручную проверить только репрезентативные места и отмеченные исключения. Группировать одинаковые причины ошибок, а не чинить сотни записей отдельными промптами.

### Приёмка

Каждая исходная фармовая группа присутствует в реестре; нет молчаливо потерянных групп. Все обычные группы либо полностью валидированы для включения, либо показаны как блокирующие пробелы — `NEEDS_GEODATA` не входит в процент готового игрового покрытия. В каждом native диапазоне уровней есть достижимые подходящие зоны; Ruins of Despair включён и проверен явно. Остальные названия берутся из datapack, а не из выдуманного списка.

**Делегирование:** ChatGPT может подготовить source-derived пакет данных/генератор и статические проверки здесь по отдельному запросу. Его нельзя маркировать `GEODATA_PASS` без исполнения на фактической геодате пользователя.

## LIVE-003 — ленивая жизнь 10 000 и материализация по месту

### Что сохранить

`PhantomPopulationManager`, `PhantomPopulationEcologyService`, `PhantomScheduler`, `PhantomHistoricalBackgroundPlanner/Service`, `PhantomBackgroundModel/Service/Transaction`, существующие materialization и progression owners. Сначала измерить текущий маршрут фонового обновления, а не переписывать его по названию одного состояния WARM.

### Контрольные точки

**003-A — разделение состояний.** Логическое присутствие `доступен/занят/офлайн` не должно равняться ACTIVE/WARM/BACKGROUND. Игрок онлайн и далеко → фон; наблюдаемый/бой/party interaction → необходимая точность; настоящий offline → нет фарма. Trader — отдельная занятость. Текущее поведение WARM и ecology catch-up проверить трассировкой: отдельный `if` в одном service не доказывает остановку всей прокачки.

**003-B — редкое пакетное обновление.** Использовать прошедшее логическое время и next-due, а не сотни тиков. Начальное предложение: окно 5–15 минут с разными фазами. При среднем окне 10 минут для 10 000 персонажей нужно около 16,7 обновления/сек, а не 10 000 обновлений каждого кадра. Это расчёт количества вызовов, НЕ оценка времени SQL/CPU.

Один вызов рассчитывает приблизительное число боёв, XP/SP, обычный дроп, spoil для способного к нему персонажа, расходы и риски за интервал. Не перечислять каждый удар и каждый убитый экземпляр моба. Общие loot/XP-профили индексировать по зоне, уровню, классу/экипировке и версии рейтов. Сохранять дробные остатки/случайность так, чтобы редкие предметы не превращались в гарантированную выдачу всем. Рейды/эпики и уникальные события не производить фоновым «принтером».

**003-C — целостность.** У каждого профиля durable cursor/operation-id. Crash/retry не выдаёт интервал повторно; materialization закрывает фоновые начисления атомарно. Переход на другой уровень/профессию/экипировку делит расчёт в точке изменения, а не применяет старую доходность ко всему периоду. Перезапуск не превращается в тяжёлую догонялку всей истории за один тик. БД обновляется ограниченными пакетами, не в network/game hot path.

**003-D — самостоятельный рост.** Причины смены зоны: уровень, экипировка/ресурсы, переполнение спота, конкретная добыча. Спойлер получает и death-drop, и spoil при реально доступных Spoil/Sweep, а не только при специальном acquisition goal. Соблюдать ограничения добычи, профессий и расходников. Поддержать законную progression-цепочку 1→20→40→76 и дальнейшую прокачку, без выдачи всех профессий/навыков заранее. Неподходящая зона приводит к выбору другой, а не вечному idle.

**003-E — видимый мир.** Дешёвый пространственный индекс по текущей логической зоне. При подходе человека — выбор уже находящихся в этой зоне профилей, ограниченное reconciliation, безопасная точка и один `Player`. Уход из видимости — задержка и больший радиус выключения, чем включения. Не исчезать на глазах, в бою, при торговой операции или принятии party. Технический baseline-load не должен кратковременно публиковаться в World.

**003-F — сутки.** Несколько перекрывающихся утренних/дневных/вечерних/ночных шаблонов. Проверка всех 168 часов недели, не только 19:00. Для выбранного lively preset до safety/capacity ограничений всегда достаточно логически доступных кандидатов под боевой лимит, а пики меняют их число и состав. Это не требование всем 10 000 фармить 24/7. Europe/Warsaw лишь интерпретирует реальные часы расписания, не заменяет сами расписания и не является игровым временем суток.

**003-G — nickname scale gate.** До повышения PopulationTarget до 10 000 прогнать детерминированную генерацию 10 000 имён с учётом уже существующих characters: ноль исчерпанных name attempts, ноль итоговых дубликатов; отдельно вывести распределение CLEAN/COMPOUND/TRANSLIT_SLANG/DECORATED/DIGITS/LEET и долю numeric fallback.

### Приёмка

10 000 профилей без 10 000 Player/потоков. Фоновая очередь при заданном темпе не растёт бесконечно; budget/time cap соблюдается. Контрольные фантомы нескольких рас реально переходят из стартовых в следующие подходящие зоны. При 100 повторных циклах materialize/dematerialize нет двух владельцев, двойной награды и утечки разрешений. Математический тест охватывает уровни/классы/зоны; визуальный smoke включает старт, Ruins of Despair, среднюю, высокую зону и catacomb room.

Рост до 10 000: 1 280 → 5 000 → 10 000 с сохранением результатов каждой ступени. Не обещать, что поднятие одного INI автоматически даёт этот результат на текущем коде.

## LIVE-004 — города, удалённое общение и пати

### 004-A — сидящие торговцы

Переиспользовать native private BUY/SELL/CRAFT и торговые проверки, а не рисовать NPC с декоративной надписью. Исходные точки чтения: `data/sql/OfflineTraderTable.java`, `config/custom/PhantomMarketConfig.java`, `dist/game/config/Custom/OfflineTrade.ini`, `PhantomMarket.ini`, `dist/game/data/scripts/handlers/chat/commands/voiced/Offline.java`, существующие phantom market/commerce owners.

Отдельный лимит: 32 → 64 → 128 лавок суммарно, распределённых по городам из реального native registry. Предпочтение крупным городам, минимальное присутствие в остальных при достаточном лимите; конкретные места — свободные safe points, не дверь/GK/NPC. Доходный ассортимент связан с реальной добычей и спросом; товары и деньги конечны. Уже согласованные цены/защиту от NPC↔Phantom арбитража не сбрасывать.

У сидящего торговца нет AI боя, pathfinding и частых решений фарма; редкое переоценивание ассортимента и реакция на сделку. Он всё ещё `Player` и занимает память/видимость. Отдельный счётчик не должен обходить общий лимит настоящих тел. Штатный offline restore и Phantom restore не должны независимо поднять одного персонажа.

Важное различие: обычный человеческий `.offline` может запрещать PM. Разговаривающий автоматический торговец может быть без сетевого клиента, но логически доступен для торговли/переговоров. Не включать всем Phantom флаг offline, а затем не обходить глобально запрет лички.

**Приёмка:** реальные покупка/продажа/крафт, изменение инвентаря и баланса, исчерпание товара, отказ при нехватке денег, сохранение после restart, отсутствие дубликата Player, точный отдельный учёт торговых и боевых слотов.

### 004-B — личка профилю без тела

Точки: `ChatWhisper.java`, `Say2.java`, `model/chat/ChatObservationService.java`, существующая phantom conversation/social/identity инфраструктура. Добавить/подключить индекс «точный ник → профиль → доступность» до финального ответа «не в сети», сохраняя native chat bans, block/silence и ограничения канала.

Переписка с доступным BACKGROUND-профилем не должна материализовать его, создавать сокет и нагружать поиск пути. Сохранять ограниченную структурированную память, не бесконечный журнал каждой фразы. Доставленное сообщение не сопровождается одновременно ошибкой «не в сети». Для настоящего offline — честная недоступность; не выдавать автоматический ответ за доставку игроку.

**Приёмка:** PM туда/обратно на другом материке при нулевом приросте числа materialized; сохранение релевантного контекста после перехода состояния; block/chat ban/несуществующий ник; 10 000 профилей не обходятся на каждое сообщение.

### 004-C — приглашение и party

`RequestJoinParty.java` сейчас использует lookup по native World, далее существующий `PartyInvitationService`. Требуется законченный путь для доступного нематериализованного адресата: точное разрешение имени, bounded предложение, согласие/отказ, timeout и только затем native membership.

Для сохранения native Party материализовать согласившегося участника в его реальном местоположении перед завершением вступления, зарезервировав слот. Это допустимая целевая стратегия для маленькой партии, а не повод держать всю популяцию в World. При отсутствии слота — корректно отказать/отложить; без ghost-member и прямой вставки в список. Настоящую party на время взаимодействия удерживать в безопасном состоянии materialization.

Не телепортировать его бесплатно к игроку. Существующий personal self-only Summon Friend и штатные ресурсы/условия не расширять неявно. Приглашение издали не означает награду за чужой бой вне native XP range.

**Приёмка:** согласие/отказ; полный состав; уход/смена лидера между запросом и ответом; релог; нехватка слотов; один Player; правильное штатное распределение XP/SP при пользовательских рейтах.

### 004-D — крик

Правило доставки совпадает с реально настроенной областью native SHOUT/TRADE. Для регионального крика фоновые слушатели выбираются по логическому региону; для глобального — по соответствующей настройке, но с ограничением реакции и антиспамом. Нельзя заставлять 10 000 ботов отвечать хором или слушать региональный крик через весь мир. Не перебирать все профили для каждого сообщения.

## LIVE-005 — инстансы и финальная приёмка

### 005-A — полный реестр возможностей

Из native данных составить конечную таблицу `INSTANCE_COVERAGE.tsv`: native ID/вид, варианты, условия входа, party/reuse/resources, текущий Phantom adapter, проверенные шаги и результат. Разделить «контент существует для человека», «есть policy/backend» и «фантом самостоятельно вошёл/сыграл/вышел». Наличие Java-класса или XML не является доказательством последнего.

Обязательная цель: все native варианты Kamaloka, все 6 Rift tiers, native варианты Pailaka, все 14 обычных Catacomb/Necropolis как мировые фарм-зоны. Для прочих инстансов дать поимённый список наличия/поддержки/нужного отдельного сценария; не обещать автоматическое прохождение произвольного скрипта и не прятать его в «всё покрыто». Расширение этого списка сверх указанного обязательного набора требует отдельного решения пользователя, а не новых автоматически возникающих этапов.

Точки: `data/phantoms/quests/high-five-supported-content-v1.xml`, `data/phantoms/rift/high-five-rift-policy-v1.xml`, `java/.../phantoms/rift/`, native `DimensionalRift`/instance owners и existing supported-content executors. Существующий QOL-005 доступ и phase×spawn tests сохраняются.

### 005-B — проверка сквозных сценариев

В изолированном контуре: вход/бои/расход/награда/выход, невалидный уровень/состав, leader leave, смерть, полный instance, timeout, reuse, restart. Награда только за допустимое прохождение; фоновый пересчёт не должен обходить ограничения инстансов. Для мира — проход из уровня в уровень, покупка расходников/экипировки, разные профессии и spoil.

### 005-C — масштаб и стабильность

Профиль 10 000 managed / до 256 активных / до 128 торговцев — измеряемая цель. Снять GameServer process memory отдельно от live Java heap после GC, время GC, background throughput/backlog, p95 времени решений/материализации/PM, активные запросы навигации и SQL ожидания.

Предлагаемые критерии игрового отклика для локального ПК: PM ответ/доставка p95 до 2 с; материализация при свободном слоте p95 до 3 с; отсутствие необъяснённых здоровых активных персонажей, стоящих более 30 с без действия/причины. Диалоговые задержки по personality показывать отдельно от задержки сервера.

После прогрева: не менее 2 часов комбинированного smoke, повторный маршрут Talking Island, серия смен городов/зон, 100 циклов видимости, торговля и party. Нет необъяснённого завершения процесса, неограниченного backlog и монотонного роста live heap/числа Player на одинаковой повторяемой нагрузке. Для сравнения памяти использовать одинаковый прогретый набор, а не сравнивать пустую БД с населённой.

Завершение без вылета при неизвестной исходной причине фиксируется как `NOT_REPRODUCED`, не `FIXED`. В финальном отчёте отдельные поля: crash-root-cause, crash-regression, world-coverage, background-scale, market, remote-chat, party, instances, личный cross-class.

### 005-D — конечная фиксация

Один финальный полный `ant verify` на согласованном кодовом baseline и разрешённом тестовом контуре, затем smoke именно доставленного JAR/данных. Не выдавать один успешный build за прохождение всех сценариев. Записать SHA кода, manifest данных, пользовательский preset, исключения и остаточные риски.

После завершения этой карты новых LIVE-006… не возникает автоматически. Обнаруженный пробел остаётся явным пунктом незавершённого соответствующего этапа либо отдельно согласованным расширением — не бесконечной цепочкой «ещё один финальный gate».

## 4. Как не сжечь лимиты Codex

Сейчас при оставшихся 5% не запускать все пять этапов и не запускать полный verify ради чтения логов. Сначала собрать свидетельства без Codex. Нельзя гарантировать расход конкретного процента лимита ни для какой модели.

Перед каждым исполнением агент получает только текущий этап/контрольную точку, последний `STATE.md`, точный baseline, перечисленные файлы и относящиеся к нему тесты. Разовый исходный аудит сохраняется; повторное чтение всего репозитория не требуется. При changed baseline проверить только diff затрагивающих путей.

Генерацию географических данных делает инструмент за один проход, а не LLM, вручную сочиняющая тысячи координат. После первоначальной полной проверки запускать инкрементальные проверки по хешам изменённых источников. Ошибки группировать по общей причине.

Внутри этапа: воспроизводимый failing test → минимальное исправление → focused regression → affected smoke → checkpoint. Не переписывать комментарии/форматирование несвязанных файлов. Большие тестовые логи сохранять в файлы, агенту выводить итоги и причину первой ошибки.

Формат итогового checkpoint:

```text
STAGE=LIVE-00N
CHECKPOINT=<конкретный подпункт>
STATUS=GREEN|BLOCKED|FAILED|NOT_REPRODUCED
BASELINE=<SHA>
CHANGED_FILES=<точные пути>
TESTS_RUN=<имена/команды и результаты>
TESTS_NOT_RUN=<причина>
RUNTIME_DELIVERED=YES|NO
NEXT=<одно следующее действие>
```

Границы `UNKNOWN`, `NOT_REPRODUCED` и `BLOCKED` не разрешают объявлять функцию работающей. При нехватке лимита сохранять текущее состояние и точную команду продолжения; не оставлять частично применённую миграцию или потерянные конфиги.

## 5. Политика памяти

Для следующего этапа настройки предлагается потолок GameServer `-Xmx16g` при `-Xms2g`, сохранив остальные текущие JVM-опции. Это не изменение размера heap LoginServer и не использование всех физических 64 ГБ. До изменения сначала сохранить диагностический снимок текущего запуска.

Значение Xmx ограничивает Java heap, не всю память процесса. Нужен запас для native memory, метаданных/потоков/буферов, БД, Windows и клиента. 16 ГБ не является гарантией для любого числа персонажей; нехватка 16 ГБ сама по себе не доказывает утечку. В то же время 32 ГБ не стоит выдавать вслепую. Решение — по live heap, скорости выделения, GC и суммарному commit системы, а не по одному скриншоту диспетчера.

Не менять одновременно collector, размеры heap и численность населения во время поиска вылета. Не отключать/не урезать pagefile как «оптимизацию».
