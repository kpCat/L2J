# Интерактивная лаборатория промптов

Лаборатория — седьмая вкладка существующей WinForms Studio. Использует тот же Core, LM-клиент, workspace, реестр и компилятор Semantic V4. Модель и сервер LM Studio запускаются вручную. Вкладка не загружает модель и не меняет контекст, GPU/CPU offload, KV, template или preset. Нужен уже загруженный exact model/instance с контекстом 65536.

## Обычный цикл

Studio можно запустить с `--workspace "D:\ваша-отдельная-лаборатория"`. Откроется история, настройки и профили именно этого каталога. Без аргументов сохраняется обычный workspace в `%LOCALAPPDATA%\PhantomSemanticStudio\workspace`. Данные между каталогами не копируются, результаты не утверждаются и не импортируются автоматически. Один workspace нельзя одновременно открыть в двух процессах.

Для проверки пути без окна: `dotnet PhantomSemanticStudio.dll --workspace "D:\ваша-отдельная-лаборатория" --check-workspace` из каталога сборки WinForms. Проверка использует существующие защиты WorkspaceStore, читает настройки и обычную сессию, освобождает lock; код 0 и `WORKSPACE_OK` означают успех, код 2 — отказ с диагностикой. Default source и source из сохранённых настроек проверяются до создания каталога/lock; тот же preflight применяется при обычном открытии окна. Новый явный каталог может быть создан с файлом `workspace.lock`. Это проверка открытия workspace, а не полная проверка лабораторной истории или качества реплик. Она не инициализирует GUI, не обращается к модели и не открывает workspace по умолчанию. Относительные, пропущенные и повторные аргументы, пересечение с исходниками, junction и занятый workspace запрещены. `--workspace` нельзя совмещать с тестовым `PSS_UI_SMOKE_WORKSPACE`; ограничения smoke-режима сохраняются.

1. Откройте workspace Studio и вкладку «Лаборатория промптов». Выберите именованный профиль или создайте/скопируйте свой. SYSTEM и USER редактируются отдельно. «Сохранить версию» создаёт неизменяемую редакцию. Выбор старой версии возвращает её без удаления новых.
2. Можно начать с вкладки «Создать из описания». Опишите характеры, ситуации и желаемые реакции. «Предложить промпт и план партий» обращается к Gemma с независимыми редакционными параметрами. Предложение пока не разрешает генерацию.
3. Проверьте SYSTEM/USER и каждую строку плана: действующая leaf-категория, TRIGGER/REPLY/INITIATIVE, голос, отношение, стиль, зрелость, грубость, stance/tone, канал, число реплик. Для выбранной строки отдельно редактируются ситуация и предыстория. Последний ход диалога принадлежит игроку. Партию можно скопировать или убрать.
4. Новая категория рассматривается отдельно: показываются key/act/intent/причина и hash предложения. Утверждение меняет только реестр лаборатории. События не добавляются: INITIATIVE привязывается только к поддержанной паре существующих category/event. У REPLY/TRIGGER event пустой.
5. Нажмите «План проверен». План из описания разбивается на независимые профили семейств. Проверьте их SYSTEM/USER перед генерацией; принятие промптов и реплик остаётся отдельным действием. Взрослый контекст требует явного opt-in для каждой соответствующей сцены.
6. «Генерировать» закрепляет очередь партий выбранного профиля. «Генерировать все семейства плана» закрепляет выбранные версии всех дочерних профилей и общий идентификатор эксперимента, затем выполняет партии последовательно. Просматривайте каждую сохранённую партию через историю. Реплики отображаются строками с «Нравится», «Не нравится» и комментарием; общий отзыв относится к выбранной партии.
7. «Улучшить промпт» передаёт ограниченную сводку фактических результатов и сохранённых оценок. Gemma предлагает отдельную версию SYSTEM/USER. Она не заменяет принятую. «Перегенерировать и сравнить» закрепляет исходную сцену и параметры baseline, показывает V1/V2 рядом.
8. Повторяйте цикл. «Принять эту версию» закрепляет только промпт. История, исходные ответы и отзывы сохраняются между перезапусками. Черновики привязаны к версии; незаконченный SYSTEM тоже сохраняется.

## Параметры и диагностика

### Специализированные семейства

В `prompts/corpus001/families.v1.json` заданы 20 начальных семейств. Для генерации выбираются только короткий общий контракт, текущий режим, одно семейство, компактная инструкция категории и выбранный голос/характер/отношения/стиль/эмоциональное состояние. Сцена передаётся отдельно. Каталог всех семейных инструкций в запрос генерации не включается. Description planner получает только ID/названия и карту категорий как данные классификации.

«Создать профиль семейства» создаёт независимый профиль для выбранной строки плана. Исходный профиль, его SYSTEM и accepted pointer сохраняются. Старые пользовательские профили продолжают прежний цикл до явного перехода. В новом профиле поле SYSTEM редактирует только инструкцию семейства; на вкладке назначения отдельно редактируется инструкция категории и эмоциональное состояние. Переход в другое семейство требует новой копии/разбиения, чтобы правка торга не испортила принятый профиль поддержки.

В новых профилях `social.banter.rough` стартовая инструкция категории отдельно сохраняет речевое действие и владельца факта. Для TRIGGER просьба игрока подколоть его самого отличается от подкола, которым игрок обращается к фантому. Это помогает избежать готового ответа фантома вместо входа игрока. Сохранённые версии не обновляются автоматически: новую инструкцию можно проверить через новый профиль либо явно сохранить собственной версией. Этот стартовый вариант не означает подтверждённой естественности, отсутствия дублей или принятия production-профиля; оценки и утверждение остаются отдельными действиями.

«Разбить план по семействам» сохраняет исходный план и создаёт дочерние профили с отдельными версиями/отзывами/принятием и общей группой. После описания Gemma предлагает отдельные компактные SYSTEM/USER использованных семейств. Старые планы без таких предложений получают стартовые семейные инструкции; они не объявляются откалиброванными. Неизвестная категория без подтверждённой привязки к семейству блокирует это разбиение с диагностикой, а не получает произвольный fallback.

Каждая версия хранит точный immutable snapshot компонентов и функциональный hash. Изменение bundled defaults другого семейства не переписывает сохранённую версию. Сравнение V1/V2 использует прежнюю сцену и параметры, но компоненты новой версии. Копирование примеров отмечается отдельным advisory-флагом; текущие seed-профили не содержат примеров, ложно помеченных как принятые владельцем.

CLI `prompt-coverage` экспортирует JSON-карту 142 canonical категорий, выбранного семейства/revision и наличия специализированной инструкции. Начальный статус всех 20 семейств — UNCONFIRMED. Покрытие не доказывает естественность; выбор лучших версий требует фактических сравнений и отзывов отдельно по семье/категории. Подтверждённые экспериментальные категории не расширяют основной реестр автоматически. Итоговое число семейств ещё предстоит проверить на локальной Gemma.

Пять отдельных именованных речевых профилей: «Крепкий мат», «Вульгарный юмор», «Двусмысленности», «Взрослый флирт», «Личный интимный разговор». Они добавляются и в прежнюю лабораторию, сохраняя пользовательские профили/версии. Грубость, шутка, намёк и предметное обсуждение личной темы оцениваются отдельно. Взрослые заготовки требуют проверки плана и явного opt-in, они не разрешают генерацию сами. Метки STRONG и лексические индикаторы в тексте показываются раздельно; эвристика не определяет смысл и не доказывает качество.

Для прямого разговора предложена отдельная `life.love.intimacy`, не подмена `dating` или `double_meanings`. Утверждение применяется в реестре выбранной экспериментальной лаборатории через стандартное hash-bound taxonomy review; в исходный/server registry категория автоматически не переносится. Модельные, профильные и форматные ограничения фиксируются раздельно. Эротические сцены не являются реализованным режимом этой поставки.

Генерация и редактор имеют отдельные transport, reasoning, temperature, top_p, top_k, repeat penalty, max output, streaming и connection/idle/overall timeout. По умолчанию reasoning OFF. AUTO означает отсутствие override, а не выключенный thinking. В compatible OFF отправляется `reasoning_effort=none`, ON — `high`; native передаёт `reasoning=off/on`. Решение о фактическом применении принимается по telemetry, а не подписи в форме.

`min_p` доступен только для native API; compatible путь отклоняет его с явной диагностикой. Native поддержка документирована [LM Studio](https://lmstudio.ai/docs/developer/rest/chat); HTTP-принятие значения ещё не доказывает влияние на распределение. Requested параметры, raw response, usage, wall time и reasoning сохраняются в истории. Точный TPS выводится только при наличии token telemetry, текущий streaming progress показывает время, байты и знаки.

Контекст ограничивается консервативной UTF-8 byte upper bound, резервом 4096 и полным output budget, включающим reasoning. История на диске не включается целиком в запрос. В refine идут до четырёх худших/лучших/комментированных примеров и ограниченная сводка. Превышение бюджета — отказ с сохранённым вводом.

Streaming не разрешает принимать частичный JSON. Требуются корректное завершение, полный aggregate, schema/model/finish checks. Native fences, неверные поля/события, length, оборванный поток и повреждённый JSON отклоняются, raw сохраняется. Нет тихого transport fallback или повторного POST. Безопасный GET probe допускает один retry. Issued без durable receipt требует проверки неопределённого исхода; Resume не отправляет его повторно. Завершённые партии не повторяются; ещё не начатая очередь общего эксперимента возобновляется отдельно. Отмена сохраняет завершённые результаты и не превращает частичный ответ в успех.

## Принятый результат и отдельный pack

1. Примите удачный промпт и сохраните оценки реплик. Предпросмотр берёт только LIKE из COMPLETE/schema-valid партий именно принятой версии. При включённой группировке рассматриваются оценённые партии выбранного общего эксперимента; иначе только выбранная партия.
2. Отдельные JSONL сохраняют точные category/mode/act и исходные метаданные. Схема, идентичность источников, точные дубли и V4 dry-run проверяются существующим pipeline. Показываются распределение, предупреждения и возможные пробелы fallback. Лексические метрики не доказывают смысловую уместность.
3. Прочитайте все выбранные фразы и предупреждения. Явно подтвердите смысл и речевой акт, затем импортируйте в `labs/prompt-lab/v4-workspace`. Изменение отзывов, реестра, источника или JSONL аннулирует прежний preview. Импорт сохраняет hash-bound receipt и не смешивает данные с прежним пользовательским V4-workspace.
4. «Собрать и проверить V4-stage» использует штатный compiler. Для каждой исходящей category/mode/stance/event/relation требуется спокойный ANY fallback без facets и мата, GENERAL. Его отсутствие блокирует сборку; лаборатория не выдумывает утверждённые fallback.
5. «Создать production-профиль» явно сохраняет принятую версию, параметры, scopes, hash реестра и ссылки на оценённые реальные партии. Это заготовка для автономной кампании; новые фразы при этом не утверждаются и не импортируются.

Старые 5650 фраз не удаляются и не импортируются сюда автоматически. Pack/stage остаются внешними артефактами. Установки или включения в GameServer нет. Текущий Java consumer имеет отдельные ограничения каналов/profanity/maturity; эти ограничения зафиксированы в аудите и данным изменением не снимаются.

## Границы приёмки

Автоматические проверки защищают историю, transport, схему, изоляцию, явную приёмку и V4 compatibility. Headless control tests не показывают окна и не используют Computer Use. Статический Designer check не заменяет Visual Studio round-trip или ручную проверку DPI. Реальный технический цикл на Gemma проверяется отдельно; синтетический отзыв тестового runner не считается оценкой владельца. Не считать корпус принятым по одному schema PASS или оценке самой модели.

`MIXED_SCRIPT_TOKEN_REVIEW` отмечает смешение кириллицы и латиницы внутри слова, например повреждённое окончание ответа. Это advisory для редактора: намеренный игровой сленг тоже возможен. Отдельные Latin-токены и формы вроде `PvP-пати` не запрещаются. Диагностика не исправляет текст и не заменяет смысловую оценку.

В сравнительных отчётах исходный `RawText` сохраняется отдельно от канонического `Text`, полученного штатным V4 reader. Метрики используют каноническое представление; проверка источника связывает исходную строку с hash-protected response. Нормализация пробелов или NFKC не выдаётся за изменение модельного ответа. Новые advisory-флаги при повторном анализе отделяются от исторически сохранённых.

## Связанные многоходовые разговоры: исследование, не runtime

Требование владельца зафиксировано: в будущем нужны связанные разговоры с памятью предыдущих реплик. Случайная последовательность коротких строк не удовлетворяет ему. Сейчас исследуется только Studio, серверная архитектура не меняется.

Read-first: существующие `DialogueLabSession`/`DialogueLabStore` сохраняют turns/messages в частный редакционный архив (200ходов/600сообщений/2MiB). Ответ PACK там выбирает прежний inspector, а Mentor даёт advisory, не генерирует полноценный диалог персонажей. Его20-call limit относится к старому mentor и не повышался. Это не доказательство многоходового Semantic V4 runtime.

Новая Prompt Lab передаёт последние до6 явно заданных сообщений через `GenerationStyleContext.Dialogue`; все records партии — альтернативы одного следующего хода. `ExperimentId` группирует эксперимент, а номер строки не является номером хода. Для последовательной проверки выбранный завершённый ответ можно включить в контекст следующего запроса и сохранить всю цепочку отдельно. История остаётся ограниченной: полный архив на диске, в API — последние ходы и явно заданное состояние сцены, с резервом в65536.

V4Entry/Wire не содержит conversationId, turnIndex, replyTo, состояния сцены или памяти. Outbound ограничен100Unicode codepoints и240UTF-8 bytes с дополнительным резервом под placeholders. Это предел одной игровой записи; он не требует ограничивать весь редакционный transcript100символами. Длинная сцена может оставаться отдельным архивом, а каждый пригодный самостоятельный ход — отдельно проверяться для V4. Простая нарезка сцены и tags вида scene/turn не создают runtime-порядок или память.

Экспериментальный proof: одинаковый синтетический торг в режимах FULL_LAST_6 и LAST_USER_ONLY, последовательное включение реально полученных ответов, смена условий и явная отмена сделки. Проверяются сохранение актуального предложения, реакция на исправление и отсутствие выдуманного завершения сделки. Схема/длина проверяются детерминированно; связность и память — отдельная редакционная оценка фактических цепочек. Прототип не импортирует сцену, не утверждает строки и не устанавливает ничего в GameServer. Для будущего runtime нужны отдельные contracts/дизайн/согласование.
## Представление входной сцены

На вкладке SYSTEM и USER выбор «Входная сцена» сохраняется вместе с версией и черновиком. По умолчанию используется прежняя JSON-сцена. «Читаемый текст и цитаты» отделяет назначение партии, настройки персонажей, ситуацию и последние ходы от точной схемы ответа. Это альтернативный prompt renderer внутри существующего клиента, не новый параметр LM Studio.

Значение `READABLE_SCENE` хранится в `PromptLabVersion.ContextPresentation`; у прежнего формата поле отсутствует. Старые версии и accepted pointers не мигрируют. При сравнении сохраняется выбранное представление нового промпта и исходная ситуация; sampler берётся из базовой партии по прежнему контракту. Refiner видит выбранное представление, но не меняет его автоматически. Предложенная версия остаётся отдельной.

Читаемые цитаты всё ещё находятся в одном USER API-сообщении. Они не включают серверную память, native chat history или порядок выполнения сцен. Роли определяет тот же штатный parser; scope, согласие взрослых, персональные ограничения, официальный header/records и schema validation сохраняются. Context/byte budget и запрет принятия частичного ответа действуют в обоих форматах. Новое представление не считается улучшением качества до реального сравнения на Gemma.
Для новых профилей фабрики используют короткий `prompts/corpus001/user-task.v1.md`: TRIGGER говорит игрок, REPLY отвечает фантом, INITIATIVE начинает фантом по указанному реальному событию. Стилевые инструкции семейств остаются раздельными. Текст замораживается в `Version.User`; новые версии ресурса не переписывают сохранённый USER или принятые профили. Этот lab-only ресурс не меняет классический `PromptProfiles.Hash` старого CorpusLab; его provenance защищён полным hash лабораторной версии. Правильная роль не означает автоматически естественную речь или принятие корпуса.
